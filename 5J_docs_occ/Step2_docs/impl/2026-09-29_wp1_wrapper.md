## Decisions
1. 🔴 act2 does not fit the "same map" literally. In the generated diaries `act2` is a 2-digit code ('51', '82', '03', ...; 37,302 of 116,160 episodes carry one) while every map key is a 3-digit ACL code ('821', ...). An exact lookup matches nothing (verified: exact run = no-act2 byte for byte). To make the change do something without adding a map entry, the copy has `--act2-match prefix2` (DEFAULT when act2 is on): a 2-digit act2 maps to a profile only if EVERY 3-digit key starting with it maps to the same profile. Result: 4 prefixes mapped (03, 31, 32, 82), 1 ambiguous and left unmapped (33: 331 and 332 differ). This is my reading of D2-4, NOT ruled: the manager must confirm or replace it. The 4J perturbation `force_two_digit_mapping` (G9.11) shows two-digit collapse was treated as an error in 4J, so the ruling matters. `--act2-match exact` and `--no-act2` both give 4J behaviour. All Part C act2 runs use prefix2.
2. DHW eligibility still uses the primary activity only (D2-7: DHW not used in 5J). Step 7 code cannot be edited, so the copy replaces `s7.load_pool` at run time with a same-body version that also keeps `acts2` (marked `# 5J change (D2-4)`); pool md5 and counts are printed by the manifest as before (n_days 5200).
3. Added plumbing flag `--shipped-suffix` (not a model change) so the dwelling-identity check compares with `..._seed1_cal2010` when `--year 2010` is used. Year 2010 chosen so the Step 9 calendar matches the cal2010 presence files and the 2010 Madrid weather; the year-2017 run exists only for the byte-identity check with 4J.
4. Presence CSVs copied to `wp1_test/inputs/` (md5 in each meta.json) and the Schedule:File paths point there (absolute, forward slashes). Appliance Schedule:File points at `wp1_test/step9_<variant>/enduse_profiles/es/`.
5. Design level (peak W) is read from the trigger's own `step9_objects_es.idf` (4 decimals), not the 3-decimal csv column.
6. `phi_zero`: E_PHI_INT kept with design level 0 (was 165 W for this building).
7. Output name: the 4J heating variable is `Zone Ideal Loads Supply Air Total Heating Energy`; cooling added likewise. Both are "Total" (include latent). Cooling uses the ideal-loads `ConstantSensibleHeatRatio 0.7` already in the 4J builder, so cooling energy contains a latent share; not changed.
