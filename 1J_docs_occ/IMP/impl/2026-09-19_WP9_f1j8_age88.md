## Why

Every census alignment file maps age code 88 ("not available") into the oldest group:
`06CEN05GSS_alignment.py:56` `if x >= 13: return 7  # 75+`, and the same three lines exist in the
2010, 2015 and 2022 alignment files. Persons affected (manager scan, plan log (p)): 1,594 in 2006,
11,586 in 2011, 26,095 in 2016, 30,908 in 2021. Age group is a matching variable, so those persons are
matched to GSS diaries of people aged 75 and over, who are at home much more than average. The question
the author must answer is only this: **is the effect big enough to be worth fixing, given that fixing it
means re-running every rebuild?** This task measures it. It changes nothing.

## Decisions

- **Person-level file choice**: used `<YEARTAG>_Matched_Keys_sample25pct.csv`, not
  `<YEARTAG>_Full_Schedules_sample25pct.csv`. Both carry `SIM_HH_ID`; Matched_Keys is genuinely
  person-level (one row per person) and much cheaper to read. If a future check wants the episode-level
  file instead, note `Full_Schedules` also carries `SIM_HH_ID` and a `Census_ID` column equal to raw
  `PP_ID`.
- **Link key (M2)**: raw census `PP_ID` == person-level file `PP_ID` (same column name, same values;
  Matched_Keys is built by carrying the census dataframe through unchanged except for harmonized
  columns) → then person-level file `SIM_HH_ID` is used against the grid file's own `SIM_HH_ID`. This is
  the literal "the link is SIM_HH_ID" instruction plus the `PP_ID` step needed to recover which raw
  persons were code 88 (harmonization overwrites `AGEGRP` to 7 for both raw 13 and raw 88, so the
  person-level file's own `AGEGRP` cannot distinguish them — only the raw census file can).
- **M1 denominator** ("survive into matching"): `raw AGEGRP > 2`, exactly the task doc's parenthetical
  (`AGEGRP <= 2` = dropped children). No other filtering (e.g. did not additionally drop 99-type codes;
  the real alignment code does not special-case them for census either).
- **"weekday/weekend 09-16"**: `Hour` in `9..16` inclusive (8 hourly rows per household per day type).
- **"night hour 3"**: task doc does not say weekday-only or weekend-only for this one metric, so I pooled
  both `Day_Type` rows at `Hour == 3`. If the author wants it split by day type, that is a one-line change
  in `wp9_f1j8_age88.py` (`h3_mask`).
- **M4 "recomputed" value**: identical to M3's `weekday_09_16.unaffected_mean` (same slice, same
  households) — computed via the same code path, not duplicated logic.
- Script always tries all 4 census years even if one year's link fails; a failed year is marked
  `NOT_EVALUABLE`, excluded from `d`, and does not stop the other years (each year is independent).
- Script never raises on the specific "no shared key" case (returns gracefully, logs
  `LINK: NOT AVAILABLE -- ...`, `sys.exit(0)` at the end of `main()`); it does **not** blanket-catch
  unexpected exceptions elsewhere, so a genuine bug or a truly malformed real file will still show up as
  a nonzero exit / traceback in the log rather than being silently swallowed.

### Audit: is the 2006/2016 "0 affected households" really zero? (second employee pass, same day)

Zero households linking in two of four years, next to non-zero counts in the other two (1,782 and 3,502
out of thousands), looked like it could be a join bug rather than a real result, so before trusting the
`d` above I checked it directly against the raw cluster files (not the script's own output):
- Pulled 20 real raw-census `PP_ID` values with `AGEGRP==88` from `cen06_filtered.csv` via `head`/`grep`
  (some with ordinary, non-missing labour-force codes, not just obviously-invalid rows).
- `grep`'d each one **at its exact field position** (`^[^,]*,[^,]*,[^,]*,<id>,`, i.e. the `PP_ID` column,
  not a free substring match — a first unanchored attempt gave false positives against unrelated numeric
  fields like `VALUE`/`INCTAX`) in `06CEN05GSS_Matched_Keys_sample25pct.csv`.
- **None of the 20 appear.** Against a 25%-household-sample file, seeing 0 of 20 by chance if age-88
  persons survived matching like anyone else has roughly a 0.3% probability, so this is systematic, not
  sampling noise: for 2006 (and, by the same pattern, 2016), the specific persons coded 88 do not reach
  the buggy `alignment.py` age-mapping step at all — something upstream of alignment already drops them.

This means the `M4 diff = 0.000000` for 2006 and 2016 is a **true zero, not a broken measurement**: the
bug this task investigates has zero opportunity to bite in those two years. It does not change `d` (still
0.007813, from 2021) or the decision-rule outcome, but it does mean the "leave the code alone, name it as
a limitation" option, if the author picks it, is even safer than the headline number alone suggests for
half the rebuilt years. Root cause of the upstream exclusion was not chased (out of scope: this task
measures, it does not explain or fix the pipeline).
