## Decisions

- **BLOCKED at the start of T3, not a code/patch problem.** T3 says "Copy in ... only the inputs T1
  found (from the GSSCanada mirror ... or by `scp` from local if the mirror lacks them; compare md5 of
  mirror vs local for each and record)." T1 found that the direct aggregation input,
  `Full_Expanded_Schedules_Refined.csv`, **does not exist locally at all** (the intermediate files were
  cleaned up after the original April run, keeping only the final `BEM_Schedules_2025.csv`), and **does
  exist on the cluster mirror but for a visibly different, ~70x-smaller population** (see Verified).
  Neither source gives a file that would let this task reproduce the same population the paper's
  published 2025 file uses -- copying the mirror's version would silently rebuild the grid/hhsize files
  from the wrong households, and there is no local copy to `scp` instead.
  The only way to regenerate a matching-scale `Full_Expanded_Schedules_Refined.csv` is to re-run Step 2b
  (`run_profile_matcher`, `MatchProfiler`) and Step 2d (`run_postprocessing`) on the local Step-1/2a
  outputs that DO exist and DO look population-matched (`Generated/forecasted_population_2025.csv`,
  `forecasted_population_2025_LINKED.csv`, `Aligned_Census_2025.csv`, all local, all from the same
  April 8-23 timestamp cluster). But the task doc's own Task section says explicitly: **"Do NOT re-run
  Step 1 (the CVAE) or the matching ... so only aggregation + conversion change."** Re-running the
  matching step is exactly what regenerating this file would require, and I am not authorized to decide
  that trade-off myself -- it changes both the scope (a third pipeline stage, not two) and the risk
  (matching is not obviously deterministic/reproducible without checking for fixed seeds, which this
  task never asked me to check). Stopping here per the task doc's own instruction: "If blocked, set
  Status: BLOCKED with the exact reason and stop."
- **P5 not applied to 2025** (see Patches) -- a positive finding, not a gap: read the full converter
  body and confirmed there is no NaN-tier `max()` line to guard.
- **P2/P3 "active" print placed once per real invocation, not per household.** `_aggregate_household`
  runs once per `(SIM_HH_ID, Day_Type)` group -- tens of thousands of times in a real run -- so its
  "active" line is gated to print only on the first call (module-level flag in the driver), not
  repeated every time. `process_households` runs exactly once per script invocation, so its line is
  printed unconditionally at the top of the function with no gating needed. Both interpretations
  satisfy "prints its own line when it runs" without flooding the job log (memory rule 58 is about the
  line being genuinely present and checkable, not about it appearing thousands of times).
- **Driver placement:** the task doc's own path suggestion is inconsistent (`Why` section says
  `/speed-scratch/o_iseri/1J_rerun/occ/`; T3 says the staging base is the new
  `/speed-scratch/o_iseri/1J_rerun/occ2025/...` tree). Followed T3's precise structure: the driver is
  written to live at
  `/speed-scratch/o_iseri/1J_rerun/occ2025/code/eSim_occ_utils/25CEN22GSS_classification/wp9_1c_2025_rebuild.py`
  (i.e. inside the uploaded `25CEN22GSS_classification/` folder, beside `run_step2.py`/`run_step3.py`/
  `previous/`) once T3 resumes -- not yet uploaded, since T3 is blocked. This placement is required, not
