Left alone, a P5b failure would sit in the JSON while the process still exits 0 whenever P0–P5's original criteria all pass — exactly the "check that cannot fail in a way anyone would notice" pattern the doc's own P5b rationale warns about. I folded P5b's `missing_or_empty` findings into the existing `fail` accumulator so a broken P5b control changes the exit code too; documented inline in `t29_check.py`'s `main()`. Rationale: "exit code 1 is the correct outcome of a control run" (task doc) — if the *job's* exit code inherited the controls step's expected 1, `sacct` would show a "FAILED" job for a control behaving exactly as designed, inviting the misreading the task doc explicitly warns against.
