**Q2 — person table / frame.**
Not a GSS respondent file and not "2022 stock with diaries redrawn from 2022" — it is the **frozen 2022
dwelling stock frame**, diary-swapped per cycle. `STOCK = .../0_Occupancy/Outputs_21CEN22GSS/aug_pipeline/
21CEN22GSS_aug_Full_Aggregated_excl.csv` (`Step8_docs/08_gen_cycle_schedules.py:32`), loaded once and
reused for every `--year` in the run (`08_gen_cycle_schedules.py:286-294`). Docstring states the method
explicitly: "Assemble onto the FROZEN 2022 dwelling frame (aug_Full_Aggregated_excl): swap each stock
person's hom30/act30 for a stratum-matched draw from the raked cycle pool (seed=42) -> 'freeze stock,
evolve occupancy'" (`08_gen_cycle_schedules.py:11-13`). This is consistent with T16's finding that
2005/2010/2015 share one frozen 144,507-ID frame (not independently re-verified here — no household count
was run per the Q4 instruction to avoid loading multi-MB CSVs).

**Q3 — donor/diary selection filter.**
Restricted to `CYCLE_YEAR == year`, one line, no fallback across years: `pool = aug[aug["CYCLE_YEAR"] ==
year]` (`Step8_docs/08_gen_cycle_schedules.py:253`). The demographic-match fallback tiers (T1..T4,
`08_gen_cycle_schedules.py:56-59`, applied in `demo_assemble` at `183-224`) only widen the demographic key
set — they never widen the year: `pool` is already year-filtered before `demo_assemble` is called
(`gen_cycle`, `251-258`), and even the T4 "strata-only" failsafe still draws from that same year-filtered
`pool`. `complete_day_types` (`96-146`), which donor-draws a household's missing weekday/weekend row, also
draws only from within the already-assembled (hence already year-specific) frame — it groups on the
post-assembly dataframe, not on `aug`.
Real vs. synthetic: **not filtered to real-only.** The pool keeps both `IS_SYNTHETIC==0` (observed) and
`IS_SYNTHETIC==1` (synthetic) rows — reported explicitly: `print(f"  pool: {len(pool):,} rows (obs
{(pool.IS_SYNTHETIC==0).sum():,} / syn {(pool.IS_SYNTHETIC==1).sum():,})")` (`08_gen_cycle_schedules.py:
254-255`). `rake_cycle` (`150-174`) only re-weights synthetic `hom30` slots toward that year's OWN
observed within-stratum marginal (`obs_m = hom[(~syn) & (strata == s)].mean(...)`, line 159) — it does not
pull in another year's diaries.

**Q4 — CYCLE_YEAR column on intermediates / outputs.**
Intermediate carries it: `outputs_step4/augmented_diaries.csv` header field 2 is `CYCLE_YEAR`
(`2J_docs_occ_nTemp/outputs_step4/augmented_diaries.csv:1`, checked via `head -1`/`Get-Content -TotalCount
1`, file not loaded). Final on-disk outputs do NOT carry it: `BEM_Setup/BEM_Schedules_2005.csv:1`,
`BEM_Schedules_2010.csv:1`, `BEM_Schedules_2015.csv:1` headers are all identically `SIM_HH_ID,Day_Type,
Hour,HHSIZE,DTYPE,BEDRM,CONDO,ROOM,REPAIR,PR,MATCH_TIER,Occupancy_Schedule,Metabolic_Rate` — no
`CYCLE_YEAR` field, matching the script's fixed `OUT_COLS` (`08_gen_cycle_schedules.py:41-42`), so a
per-year mix cannot be audited from the output file alone; the only year-provenance is the generating
script's own filter (Q3) plus the two 2026-04-02 / 2026-06-08 backup timestamps as run evidence.
If a real per-year row-count audit of the donor pool is wanted, the one-liner for a Speed job (not run

line-for-line (Q1 "exact command" is NOT FOUND); the verdict rests on current script logic + provenance
