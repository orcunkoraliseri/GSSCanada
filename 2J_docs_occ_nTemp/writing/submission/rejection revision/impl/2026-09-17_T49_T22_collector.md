looks at proves nothing and makes a working checker look blind.

## Decisions
(anything this doc did not decide, and what you assumed)

- **B4 reference file is `step9_manifest.csv`, not a per-cell `cell_manifest.csv`.** The doc allowed
  for the possibility that no per-cell manifest could be found and said to mark B4 `NOT_EVALUABLE` in
  that case. I judged that `step9_manifest.csv` is a strictly better find, not an absence: it is a
  published, campaign-owned file (not T22's own manifest, not a re-derivation of the seed-42 draw)
  that names both `cell` and `hh_id` directly, so it answers the exact same question a per-cell
  `cell_manifest.csv` would. B4 is therefore scored as PASS/FAIL, not `NOT_EVALUABLE`. If the manager
  disagrees this file counts as "the published campaign's own cell_manifest.csv", the fix is a
  one-line argument change (`--published-manifest`) to point at a different file — nothing else in
  the checker depends on this choice.
- **B4 control uses a synthetic baseline, not a copy of T22's real `cell_manifest.csv`.** The Brief's
  literal wording ("copy the cell's `cell_manifest.csv`... change one household ID value") assumes a
  control built from T22's real per-cell manifest would otherwise match the published set exactly
  except for the one deliberately mutated row. The spot check above shows that assumption does not
  hold here — T22's real IDs already differ from the published ones before any mutation, for reasons
  GATE_B4 itself exists to surface. Building the control from T22's real manifest would have made
  "exactly one ID present only in T22, one only in the published set" impossible to construct or
  verify. Instead, `build_b4_control()` in `t49_check.py` builds the control's un-mutated baseline
  directly from the published manifest's own IDs for the control cell (so it is defined to match
  perfectly before mutation), then mutates exactly one entry. This tests the checker's set-comparison
  logic in isolation, with a known ground truth, independent of whatever the real T22-vs-published
  relationship turns out to be. The **real GATE_B4 scoring is unaffected** — it always compares T22's
  actual, unmodified `cell_manifest.csv` files against the actual, unmodified `step9_manifest.csv`.
- **B2 control uses symlinks for the 48 untouched households**, not a full byte-for-byte
  `cp -r` of the whole cell (which would duplicate ~50 EnergyPlus household output trees). The
  Brief's "copy one cell directory" is satisfied by copying `cell_manifest.csv` for real and giving
  each unperturbed household a symlink to its real `static/hourly_meters.csv` (read-only reference,
  never opened for writing) plus two independently-materialized files for the truncated and deleted
  households. The real T22 tree is never opened for writing anywhere in the script — verified by
  inspection of `build_b2_control()`, which only ever calls `open(..., "r")` on paths under
  `real_cell_dir`.
- **"Successful run" for GATE_B2** is not a field in `cell_manifest.csv` (there is no status column —
  only `sample,sim_hh_id,hhsize,dtype,pr`). I defined success as: the household's
  `static/hourly_meters.csv` exists AND has exactly 8761 lines. This is the same coordinate B2's PASS
  condition names explicitly, so it should not be controversial, but it is a definition this doc did
  not spell out verbatim and I am flagging the assumption.
