## Design (manager, fixed before data)

- **Persons:** the T18 Arm N stock (`21CEN22GSS_aug_Full_Aggregated_excl.csv` of Arm N). Each person keeps
  their own 2022 diary. No random redraw: `assemble_2030` (`07_aug_to_bem.py:182-193`) is **not** called.
- **Targets per day stratum s (weekday 1, Sat 2, Sun 3) and slot t (48):**
  `target[s,t] = clamp(stock_rate[s,t] + 8 × pre_slope[s,t], 0, 1)`.
  `stock_rate` = unweighted person mean of `hom30` over stock persons in stratum s (plain mean, as
  `07_aug_to_bem.py:97`). `pre_slope` = exactly the `06_forecast_rake.py:138-165` computation (real
  2005/2010/2015 respondents of the full `augmented_diaries.csv`), imported or copied with line citations.
- **Rake:** the existing binary-flip rake of `06_forecast_rake.py` (seed 42, run-boundary preference,
  joint mode keeps `act30` consistent), called on the stock person rows per stratum. Import the function;
  if it is not importable without side effects, copy it verbatim with a citation. No source edits.
- **Then** the same `complete_day_types` + `convert` path the 2022 year uses (`07_aug_to_bem.py:148-180`,
  `:94-109`), same seeds, writing `BEM_Schedules_2030.csv` under `T20/out/main/`. A wrapper replaces only
  the step that builds the 2030 person table; everything after it is the pipeline's own code.
- **Two runs:** `null` (pre_slope ≡ 0) and `main` (real slopes). Same code path, one flag.

## Decisions
- **Monkeypatch technique reused from T18, applied to `assemble_2030` itself rather than to a path
  constant.** `07_aug_to_bem.py`'s own `main()` (`:195-233`, unedited) is driven end-to-end; the
  ONLY module attribute this wrapper overrides is the function object `a2b.assemble_2030` (normally
  `07_aug_to_bem.py:182-193`, a random redraw from a 2030 pool file) — replaced with a closure
  returning the already-computed 2030 person table. `a2b.BEMS` is also set (needed by `main()`'s
  write-tail, `:219-228`) to this job's own `out_dir/BEM_Setup/`, never a real repo path. `AUG`/
  `D2030`/`D2030_JOINT` module globals inside `07_aug_to_bem.py` are left untouched (unused for
  `--year 2030` once `assemble_2030` is replaced).
- **Rake target formula implemented exactly as designed:** `stock_rate[s,t]` = plain unweighted
  person mean of `hom30_t` over Arm N stock rows in stratum `s` (own code, `07_aug_to_bem.py:97`
  pattern, per-stratum instead of per-household); `pre_slope[s,t]` = `06_forecast_rake.py`'s own
  `project_to_2030()` slope, called on `--diaries` (the FULL `augmented_diaries.csv`, never the
  2022-only Arm N filter file); `target = clip(stock_rate + 8*pre_slope, 0, 1)`. `null` mode forces
  `pre_slope` to an all-zero `(3,48)` array before this formula, same code path otherwise — matches
  "Two runs ... same code path, one flag."
- **"Joint mode keeps act30 consistent" implemented as: run `rake_2030()` (hom30 binary flip) on the
  stock rows with T20's own `target` array, then run `06_forecast_rake.py`'s own
  `_joint_act30_rake_2030()` unedited on the raked result**, monkeypatching only its `_AUG_PATH`
  module global to `--diaries` (T18-style: never rely on the module's own file-relative BASE). This
  function's own hom30-byte-unchanged assertion is the mechanical guarantee that the act30 step never
  perturbs the just-raked occupancy target.
- **Validator calibration reference (`D2030_JOINT`) monkeypatched to THIS run's own
  `t20_person_table_main.csv`, not left unstaged.** T20 has no separate "2030 forecast pool" file the
  way the real pipeline does — the stock persons ARE the pool here. Read (Ledger/Verified above) that
  leaving `D2030_JOINT` unstaged degrades gracefully (`self.diary=None`, checks 3.3-3.5 collapse to
  one WARN) rather than crashing, but that would make the acceptance test's literal "28/28" unreachable
  for a reason unrelated to build correctness. Decision: point `bval.D2030_JOINT` at the run's own
  persisted 2030 person table (written by `t20_d1.py` before the validator step) — the faithful
  analogue of "the file the BEM was built from," matching the real pipeline's OD-3 precedent
  (validate against the file that fed the conversion, not a fixed default). Flagged as a decision the
  collector/manager should see, not a silent substitution — recorded here and in `t20_d1.py`'s
  `run_validator()` docstring.
- **Two extra artifacts persisted beyond the three named scripts' minimum, so N0/N1/R-rake can be
  recomputed from disk rather than trusted from the job log** (feedback_verify_progress_log_claims):
  `t20_targets_<mode>.csv` (stratum, slot, stock_rate, pre_slope, target — the exact numbers the
  rake was told to hit) and `t20_person_table_<mode>.csv` (`HH_ID`, `DDAY_STRATA`, `DTYPE`, `BEDRM`,
  `ACT_COLS`, `HOM_COLS` — the post-rake, post-act30-step 2030 person table). Neither is named in the
  brief's three-script list; both are outputs of `t20_d1.py`, not new named deliverables.
- **N0/N1 read directly from the two 17-col `BEM_Schedules_*.csv` files** (join on `SIM_HH_ID` +
  `Day_Type` + `Hour`), not from the 48-slot person tables — the acceptance text itself compares
  "`BEM_Schedules_2030.csv` occupancy columns" to "Arm N `BEM_Schedules_2022.csv` occupancy columns."
  R-rake instead reads the 48-slot `t20_person_table_<mode>.csv` against `t20_targets_<mode>.csv`,
  since the BEM files are hourly/rolled/reshaped and not directly the 48-slot rate the rake targeted.
- **N3 md5 done as `md5sum` inside `t20_job.sh` (bash, on the compute node), not via
  `t20_metrics.py`'s python md5.** `t20_metrics.py` still exposes `--action md5` (a thin `hashlib.md5`
  wrapper) per the brief's "N3 md5" listing under `t20_metrics.py`, but the job itself uses the
  simpler, faster bash `md5sum` + `diff` for the actual before/after gate (matches T18's own "md5 and
  filtering go inside jobs" precedent) — both paths compute the identical algorithm on the identical
  two files, so this is not a second, divergent implementation.
- **Resource sizing:** array tasks sized `-c 8 --mem=64G`, matching T18/T12 precedent for a
  similarly-scaled CSV job (Arm N stock is on the same order as the full `Full_Aggregated_excl.csv`,
  ~285,367 person-rows). Did not shrink to fit under the 32-CPU cap given T18's own array was already
  running 16 of our CPUs and T17's array another 16 (32 total) at T20's submission time — per the
  task doc, "or let the job queue" is explicitly allowed; T20 waits on `afterok:1328301` regardless.
