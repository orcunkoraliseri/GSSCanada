## Finding: 11.4 was already satisfied by 11.3's own construction, not by new work

Work item 11.3's runner (`tools/4thJ_step11_trigger_campaign.py`) already implements
the full substance of 11.4, built the same day as the runner (2026-09-08) and run for
real at last+236 (2026-09-12):

1. **The partition is fixed data, not a per-building decision that could vary or
   drift.** `STEP10_END_USES = frozenset(["space_heating"])`,
   `STEP11_END_USES = frozenset(["appliance_electricity", "dhw"])`
   (`4thJ_step11_trigger_campaign.py:119-120`). Every `C2` building's `space_heating`
   is reconstructed by Step 10; every drawn flat's `appliance_electricity` and `dhw`
   are simulated by Step 11. The two sets are disjoint by construction, so "one path
   per end-use per building" holds identically for every building the campaign runs
   on -- there is nothing to resolve per building because the assignment never varies.
2. **`check_seam` (`S10`, `4thJ_step11_trigger_campaign.py:424-438`) refuses, by
   name, before any output is written, if that ever stopped being true** -- either
   an end-use appearing on both paths (the double-count `G11.15` exists to catch) or
   an end-use on neither. It is called unconditionally in `main()` before the
   preflight prints anything (`:634`). It held silently on both real runs (Bologna,
   London); a silent hold is not "untested" -- the refusal fires on a doctored
   `STEP11_END_USES` including `"space_heating"` (verified below).
3. **The assignment is recorded in the manifest**, per building, by declaration
   rather than per row: `population_declaration()`'s `accounting_paths` field
   (`:549-556`) is written into every manifest's `declaration` block. Verified
   directly against the real last+236 output (not re-derived from memory):

   ```
   declaration.accounting_paths = {
     "step10": ["space_heating"],
     "step11": ["appliance_electricity", "dhw"],
     "note": "One path per end-use per building (G11.15). ..."
   }
   ```

   present byte-identical in both `Step11_docs/outputs_step11/c2_it/step11_11-3_it_reseed.json`
   and `.../c2_uk/step11_11-3_uk_reseed.json` (checked directly, first 4000 bytes of
   each file, `declaration` sorts before `flats` under `sort_keys=True`).

## The one open edge this closure does NOT claim to cover

The 49 buildings excluded from Step 11 (42 Bologna + 7 London, floor-averaged-diary
seam, last+236) have NO Step 11 flats and therefore no `appliance_electricity`/`dhw`
simulated for them at all. For those buildings Step 10's reconstruction still only
covers `space_heating` -- `appliance_electricity`/`dhw` are on **neither** path for
those 49 buildings specifically. This is not a seam violation (nothing is double-
counted) and it is not new: those buildings already carry "no Step 11 data" as a
flag, decided by the author at last+236. Recorded here so a later aggregate (11.5)
does not silently treat "excluded from 11.3" as "accounted for by 11.4" -- it is
declared absent, not zero.
