## 3. 🔴 WHY THIS IS NOT A TAUTOLOGY, SETTLED BY A CASE AND NOT BY A CLAIM

The audit asserts three things it could find false.

**1. The rows are the same rows.** `activity_appliance_map.csv` and `citations.csv` are hashed
and their md5s and row counts printed on every run. ⚪ This is not hypothetical: `citations.csv`
**has already changed once**, on 2026-08-27, when `D-S11-1` directive 1 added `FUENTES-2018`.

**2. The bars are the same bars.** The expected verdict and count are parsed out of the
**inheritance column** of `4thJ_11_stockEndUseLoads_val.md` — `` `G9.1` (PASS 61) `` — never from
a constant in the runner. 🔴 A constant there would have been chosen by the same hand that
wrote the runner and would have agreed with it for that reason and no other. A re-score that
disagrees with the inherited count is a **FAIL**, whatever the gate's own verdict says.

**3. The code is the same code.** `g9_1`–`g9_4` are **imported** from `4thJ_gates_step9.py` and
re-filed under `G11.x` IDs. ⚪ Re-implementing them here would have produced a second opinion,
and **a second opinion is not an inheritance** — the two could have agreed by luck and diverged
silently later.

🟢 **The case that proves it.** `drop_rows_to_20` truncates the mapping to twenty rows and
leaves every one of them well-formed. **Every gate's own verdict stays `PASS`** — twenty rows
that all name a table satisfy `G11.1` exactly as 192 do — **and the audit FAILS anyway**, on the
inherited count. That is the whole content of the word *carry-over*: it detects mapping **drift**,
not merely mapping **badness**, and drift is the thing a re-score of an unchanged file is
supposed to be watching for.

## 5. 🔴 `FINDING 168` — ONE ID, TWO GATES, AND WHY A SET COULD NOT SEE IT

**What happened.** `D-S11-2` was ruled and closed on the evening of 2026-08-27 and its DHW
per-dwelling arm was declared in section B as `G11.15`. Section D had already given `G11.15` to
the double-count gate on 2026-08-26. Two rows, one ID, in the document the runner reads to decide
what it must score.

**Why the existing guard could not catch it.** `V11.g` — *the declared suite is the scored suite*
— is implemented as a set comparison, and Step 9's `declared_gate_ids()` builds its declared set
with `set(re.findall(...))`. A set collapses the duplicate. The comparison would have read
seventeen declared against seventeen scored, reported a match, and printed a green coverage
clause over a suite with a gate missing from it. ⚪ **The guard was not wrong; it was
answering a different question.** Set equality asks *did we score what was declared*. It cannot
ask *was the declaration itself well-formed*.

**The repair.** The newcomer moved: the DHW arm is **`G11.18`**. The older ID stayed because the
implementation document, the pipeline master and `V11.d` already reference it, and because
nothing had been scored under either — so the repair is a renumber, and no verdict, count or
threshold moves.

🔴 **The detector, not just the repair.** `declared_gate_ids()` now censuses gate-table **row
heads** and returns the duplicates, and `run()` raises before scoring anything when there are
any. `duplicate_gate_id` is a registered case in the battery: it rewrites a copy of the document
so `G11.1` heads two rows, and the runner must refuse. Caught by census rather than by a run,
because a run would never have raised its voice.

⚪ **The transferable part.** It is the same shape as `D-S11-2`'s lesson one day earlier: a
mechanism that is right about the question it asks can be silently blind to the question next to
it. There, retiring a gate's verdict retired its mutation detector. Here, a set comparison that
correctly checks coverage cannot check well-formedness. **Both cost one line to ask about.**

## 6. ⚪ WHAT 11.1 DOES NOT ESTABLISH

is read. The four gates score a mapping table, which is scale-free — which is exactly why 11.1 is
the one Step 11 item that can run before a cell exists. 🔴 **It says nothing about `G11.6`,
`G11.7` or `G11.12`**, the three that carry Step 9 failures and the `INFO` classification into
Step 11, and it must never be quoted as Step 11 having a board.

**`G11.14` is out of scope, deliberately.** The work-item row says *the Step 9 mapping, trigger
and citation set*, and the trigger gate is `G11.14` — but its gate list is `G11.1`–`G11.4`, and
`G11.14` asserts the trigger's runtime columns against the **generated diaries**. Step 11's
diaries are Step 10's per-building `N_u` sets, which do not exist yet. Scoring it against Step 9's
diaries would have answered a question about Step 9 and filed the answer under a Step 11 ID.
⚪ Recorded here rather than resolved quietly, because the prose and the gate list of that
row do not say the same thing.

⚪ **One stale constant left where it is, deliberately.** `4thJ_gates_step9.py` still carries `DECLARED_GATES = ["G9.%d" % i for i in range(1, 15)]` — fourteen, written before `G9.15` existed. It is **dead code**: nothing reads it, because `declared_gate_ids()` reads the document instead, which is the whole point of that function. Recorded rather than edited, because Step 9 is closed and a cosmetic touch to a closed step's gate file is a worse trade than a line in this record. 🔴 If it is ever wired to anything, it is wrong.

**`V11.f` holds.** No `G9.x` or `G10.x` verdict is written by any Step 11 artefact. Asserted twice
— the board refuses such an ID at `add()` time, and the serialised JSON is scanned for one before
it is written.
