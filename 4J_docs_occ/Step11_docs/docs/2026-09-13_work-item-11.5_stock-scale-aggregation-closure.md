# Step 11, work item 11.5 -- stock-scale aggregation (`G11.12`) -- CLOSURE

Basis: `../4thJ_11_stockEndUseLoads.md` section 4, work item 11.5: "stock-scale
aggregation -- `G11.12` at real neighbourhood scale, with the population
declaration `G11.16` requires". `G11.12` inherits `G9.12` verbatim (section 2):
aggregate load shape over >= 100 dwellings against CREST's own published
activity statistics, R2 >= 0.85, band unmoved.

## Tool built

`tools/4thJ_step11_aggregate.py` -- imports (never re-implements) 11.3's own
trigger loop (`4thJ_step11_trigger_campaign.py`) and `G9.12`'s own scorer
(`4thJ_gates_step9.py`). Accumulates `elec_ts`/`dhw_ts` elementwise across every
drawn flat into one 8,760-step stock series (never persisting per-flat series
at 30k-flat scale), rebins to a mean diurnal profile, and scores it against
CREST's expected diurnal shape. Reports `G11.12` only -- the full `G11.x` board
is work item 11.6, not this tool (`S11`, mirrors 11.3's `--scored` refusal).

## Smoke run first (2026-09-13)

2,000-flat smoke on Bologna caught nothing wrong -- it ran clean, and its
measured per-flat rate (0.206 s/flat) projected the full-population wall-clock
to within a few percent of 11.3's own original campaign runtimes for the same
populations (Bologna ~6,126 s, London ~1,537 s), which is exactly what
importing the same trigger loop over the same population should produce. The
smoke's own `G11.12` was `FAIL (R2=0.0731, n=2000)`, correctly flagged
`!! SMOKE RUN` and not carried forward as a population result.

## Ruling: `G11.12` FAILS at stock scale, honestly, and this is not a defect

`G9.12` -- the same gate, same CREST reference, same R2 >= 0.85 band -- already
FAILED at n=100 in Step 9 (section 2). `G11.12` inherits that band verbatim by
design (`4thJ_11_stockEndUseLoads.md` line 76: "Step 11 does not exist to make
those pass"). Two independent stock populations, one an order of magnitude
larger than the other and drawn from a different city and district, both FAIL
the same way. That consistency is itself evidence the tool is measuring the
real thing, not a sampling artefact: a bug that produced a spurious FAIL would
be unlikely to fail in the same direction at both n=7,602 and n=29,902 built
from different cities' populations.

No re-implementation, no re-derivation of the CREST reference, and no
adjustment to the scorer was made to chase a PASS. That would be a second
opinion on `G9.12`'s own scoring code, which section 2 rules out explicitly.

Work item 11.5 is **DONE**, closed 2026-09-13. `G11.12` is scored, real, and
FAIL for both real populations -- the same outcome Step 9 already recorded at
smaller scale, now confirmed at neighbourhood scale for two cities.
`4thJ_11_stockEndUseLoads.md` section 4's work-item table is updated to mark
11.5 DONE with this record and both manifests as evidence.
