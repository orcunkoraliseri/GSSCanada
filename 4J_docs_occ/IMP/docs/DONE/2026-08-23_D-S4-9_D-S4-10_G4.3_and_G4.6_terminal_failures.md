# `D-S4-9` — `G4.3`: the sign is right in every run, the magnitude is short, and the band has no recorded provenance

## 1. The measurement

`G4.3` permutes the prefix across held-in diaries and requires cross-entropy to **rise** by
`>= 0.15` nats/token.

| run | fold | leg | CE true | CE permuted | rise | verdict |
|---|---|---|---:|---:|---:|---|
| 1274884 | `es` | 4 (1B) | `0.5428` | `0.6357` | **`0.0929`** | FAIL |
| 1274964 | `uk` | 4 (1B) | `0.5237` | `0.5992` | **`0.0755`** | FAIL |
| 1281612 | `it` | 4 (1B) | `0.5609` | `0.6292` | **`0.0682`** | FAIL |
| 1286209 | `es` | 5 (7B) | `0.5289` | `0.6350` | **`0.1062`** | FAIL |

🟢 **The sign is right in all four runs.** `CE permuted > CE true` every time: the model **is**
conditioning on the prefix, and destroying the prefix costs it `0.068`-`0.106` nats/token. The gate
asks for `0.15`. It is short by roughly a third to a half — it is not near zero, and it is not negative.

## 2. What is actually wrong here, and it is ours, not the model's

🔴 `G4_3_MIN_CE_RISE_NATS_PER_TOKEN = 0.15` is the **only** band in this group of
`4thJ_step4_thresholds.py` that carries **no recorded justification**.

| threshold | justification in the file |
|---|---|
| `G4_4_MIN_MI_RATIO` | a paragraph explaining why one half |
| `G4_12_MIN_CE_RISE` | a paragraph — it reuses `G4.3`'s number, and says so |
| `G4_1_STATISTIC` | an explicit `ASSUMPTION` block |
| 🔴 `G4_3_MIN_CE_RISE_NATS_PER_TOKEN` | **none** |

I searched the step doc, the validation doc and `prereg.md` for where `0.15` comes from and found no
derivation in any of them. I record that as a **provenance gap**. 🔴 It is **not** an argument that the
number is wrong, and it is **not** a licence to move it — see the constraint box above. `G4.12` inherits
the same number, so the gap propagates to a second gate.

**One smaller thing, noted rather than dismissed:** `1`-`2` prefixes per run are left **unchanged** by
the shuffle (a permutation is allowed to fix a point). At `--ce-n 256` that is under 1 % and cannot
account for a `0.05` nats/token gap, but it does dilute the contrast slightly and nobody registered it
in advance.

## 3. What I did **not** establish

I did **not** show that `0.15` is unachievable, and I did **not** find a published figure for what
prefix-permutation CE rise a correctly-conditioning model of this kind should produce. Without that,
"the model conditions adequately but the bar was set too high" and "the model conditions weakly" are
**both consistent** with this table. That ambiguity is the decision.

## 4. The options

**(a) Ship `G4.3` as an accepted FAIL, reported with its sign.**
The board reads FAIL on all folds; the paper states that prefix permutation raises CE by
`0.068`-`0.106` nats/token against a pre-registered `0.15`, that the direction is correct in 7/7 runs,
and that the bar's provenance is undocumented. Nothing is re-run, nothing is changed. The declared
limitation is honest and the reader can see both numbers.
*Cost:* Step 4 closes with a genuine unexplained FAIL, and the same number drags `G4.12` down with it.

**(b) Same as (a), plus one measurement that would disambiguate §3 — a *scale* for the gap.**
Run the identical permutation test against a **null model** (the un-finetuned backbone) on the same
256 held-in diaries. If the base model's rise is near zero and ours is `0.10`, the fine-tune demonstrably
bought prefix-conditioning and `0.15` is simply an unsourced bar. If the base model already rises
`0.09`, our fine-tune bought almost nothing, and the FAIL is real and about the model. **This is a
one-shot, read-only, CPU/GPU job. It changes no threshold and no artefact.** It is the only option that
can tell the two readings apart.
*Cost:* one job per fold, and it may return the answer we do not want.

**(c) Declare the provenance gap a pre-registration defect and record `G4.3` as NOT EVALUABLE.**
Precedent exists — `D-S6-3` item 1 ruled `MAPE > 20 %` not evaluable as written.
*Cost:* 🔴 the two cases are **not** alike. `MAPE` was not evaluable because the arithmetic was
undefined on the published data. `G4.3` is perfectly evaluable — it computes, it returns a number, the
number is short. Calling it NOT EVALUABLE because we dislike where the bar came from would be relaxing a
band because our model failed it, which the project's own rule forbids. **I recommend against (c) and
list it only so it is visibly rejected rather than silently skipped.**

🟢 **My recommendation: (b).** It is the only option that adds information, it costs one job, and it
cannot alter any frozen number. If it must be one line: **(a) is defensible; (c) is not.**

## 1. What `G4.6` is actually differencing — two computations, not two runs

```
unmerged:   x·W  +  s·((x·A)·B)      one full GEMM, one rank-r path, one add
merged:     x·(W + s·BA)              one full GEMM on a different matrix
```

These agree in **exact** arithmetic and disagree in float32 because they **re-associate** the same
sum. That is not a defect in the merge and not noise in the hardware. It is the quantity the gate
measures, and it does not go away by computing it more carefully.

## 2. The scored board

`max_logit_diff` between merged and unmerged, band `1e-04`, measured in float32:

| run | fold | leg | `max_logit_diff` | positions | verdict |
|---|---|---|---:|---:|---|
| 1274884 | `es` | 4 (1B) | `3.471e-04` | 20103 | FAIL |
| 1274964 | `uk` | 4 (1B) | `3.223e-04` | 16554 | FAIL |
| 1281612 | `it` | 4 (1B) | `3.853e-04` | 16706 | FAIL |
| 1286209 | `es` | 5 (7B) | **`7.279e-04`** | 20103 | FAIL |

## 3. 🟢 The alpha sweep — job `1274944`, on disk since 19 August, and it settles the gate

The sweep scales the adapter's `B` by `alpha`, so the merged delta becomes `alpha·s·BA`, and reads the
gate's own statistic at each `alpha`. Fold `es`, Leg-4 adapter, float32, `tf32 matmul=False`, **20103
positions at every single row** — so position count is held constant across the whole table.

| `alpha` | `max_logit_diff` | verdict at `1e-4` | what the adapter contributes |
|---:|---:|---|---|
| `1` | `3.471e-04` | FAIL | the full trained delta |
| `0.1` | **`1.034e-03`** | FAIL | one tenth of it |
| `0.01` | **`1.238e-03`** | FAIL | one hundredth |
| `0.001` | **`6.428e-04`** | FAIL | one thousandth |
| `0` | **`0.000e+00`** | ✅ **PASS** | **nothing at all** |
| `1` (repeat) | `3.624e-04` | FAIL | contamination check |

🔴 **Read the middle of that column.** The drift does **not** shrink as the adapter shrinks.
Cutting the delta by a factor of 1000 leaves the drift **at or above** its `alpha = 1` value —
`1.238e-03` at `alpha = 0.01` is **3.6x larger** than at `alpha = 1`, at identical position count.
The sweep's own pre-declared reading applies: this is the **plateau** branch, not the linear branch.
There is a floor of order `10^-3` that has nothing to do with how much the adapter learned.

🔴 **The floor sits an order of magnitude above the band.** `G4.6` asks for `< 1e-04`. The
comparison's own floor is around `1e-03`. **The band was set below the noise floor of the computation
it bands.**

🟢 **Both of the sweep's built-in controls are clean, so this is not an artefact of the sweep.**
`alpha = 0` returns **exactly `0.0`** — `B = 0` means `W + 0 = W` bitwise, reproducing the
`freeze_adapter` result from the other direction and proving the harness can read a true zero. The
two `alpha = 1` rows differ by `1.526e-05`, **4.4 %** of the reading, so the sweep is conclusive to
that precision and the effect above is 20-80x larger than it.

## 4. The consequence, stated plainly

🔴 **`G4.6` at `1e-04` is unsatisfiable for any adapter that trained.** The only row in the sweep
that passes is `alpha = 0` — an adapter that learned **nothing**. A check that can be passed only by
an untrained model and failed by every trained one is **inverted**: on its own scale, our FAIL is the
outcome that indicates the adapter is real.

That is not a licence to move it. Per the constraint box, `4thJ_step4_thresholds.py` is frozen and
`G4.6` ships FAIL on all four scored runs. The only question was **what the FAIL is recorded as
meaning**, and that is now ruled — §6.

### `D-S4-10` — the merge-parity check

Generate from the unmerged model and from the merged model with the **same prompts** and the **same
seed**, and compare the **outputs**. 48 held-in validation diaries per fold, `max_new_tokens 1200`.

| job | fold | leg | adapter |
|---|---|---|---|
| `1286562` | `es` | 5 | `runs_leg5/leg5_primary_fold_es/adapter` |
| `1286563` | `es` | 4 | `runs/leg4_primary_fold_es/adapter` |
| `1286564` | `uk` | 4 | `runs/leg4_primary_fold_uk/adapter` |
| `1286565` | `it` | 4 | `runs/leg4_primary_fold_it/adapter` |

Script `4thJ_step4_g46_merge_parity.py` + `4thJ_step4_g46_parity.sh`, out
`4J_step4/g46_merge_parity_leg<L>_<fold>.json`.

Three things were built into it before it ran, each because leaving it out would have produced a
number that looked fine and meant nothing:

* 🔴 **The harness has its own zero.** The **unmerged** model is generated **twice** before any
  merge. Those two passes must be token-identical. If they are not, generation is not deterministic
  under this seed, the merged-vs-unmerged difference cannot be attributed to the merge, and the run
  reports **`VOID`** rather than a difference it cannot explain. This is `alpha = 0`'s analogue.
* 🔴 **Both RNGs are reset, not just torch's.** `generate_samples` draws its prompt sample with
  the `random` module. Resetting only `torch` would have let the two passes generate from
  **different prompts** and still print a comparison. The prompt keys are compared across all three
  passes and the run aborts without writing if they differ. Same class of defect as `FINDING 8`.
* 🔴 **Measured in bf16, the SHIPPING dtype — deliberately different from `G4.6` itself.**
  `D-S4-1` requires the *logit* comparison in float32, which is right for a question about
  arithmetic. This is a question about **behaviour**, and the behaviour that ships is bf16. A float32
  parity result would not be evidence about the artefact anyone actually runs. The two numbers must
  never be read as measuring the same thing.

Pre-declared: **high but not perfect** agreement is expected. A diary is 250-600 sampled tokens and
one crossed decision boundary anywhere re-rolls the whole suffix, so some diaries diverging is the
**expected** outcome, not a failure. 🔴 The number that matters is therefore **not** how many
diaries match — it is **where** the first divergence falls, which is why `first_divergence_frac` is
reported.

🔴 **What the parity check cannot do:** it cannot show the merge is correct. Identical outputs on
48 prompts bound the merge's behavioural effect **on those 48 prompts**. It is evidence about
consequence at the sample size stated, and the sample size is printed beside every number.
