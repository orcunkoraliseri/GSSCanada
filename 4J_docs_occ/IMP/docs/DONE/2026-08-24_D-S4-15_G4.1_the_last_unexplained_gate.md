## 1. Where `G4.1` stands

`G4.1` is the within-stratum variance-ratio gate. Statistic = per-diary at-home share.
Band `0.80`–`1.25`, six scorable strata (N >= 100 on both sides).

| fold | canonical (trainer-side) reading | source |
|---|---|---|
| `es` | FAIL, worst-high `1.456` as scored (`1.614` if truncated at the first `<eor>`) | job `1286546` |
| `uk` | FAIL all 3 epochs; ep2 = 1 below / 3 above, worst `0.707` / `2.293` | job `1286547` |
| `it` | FAIL / FAIL / **PASS** on ep2 — the only clean `G4.1` in the project | job `1286548` |

Two things are already settled and must not be re-opened:

* **`D-S4-11` (i)** — the TRAINER's `gate_g4_1` (`4thJ_step4_train.py:638`, real side
  `real_ref`, 54,114 diaries) is canonical. The seventeen perturbation-side `G4.1` FAILs
  had `n_scorable_strata = 0` and are `NOT COMPUTED`, never FAIL. The "two implementations"
  lead in `RESUME.md` is therefore CLOSED; it was a support failure, not a variance one.
* **`G4.7` is not the cause.** Truncating the generated text at the first `<eor>` moves the
  worst ratio the WRONG way (`1.456` -> `1.614`).

So the only live question is the band branch itself: the generated at-home share is
**over-dispersed** relative to the real one, on two folds out of three, and we do not know
by how much that exceeds pure sampling noise.

---

## 2. The measurement that is missing, and it is the same one that settled the other gates

Every gate Step 4 has disposed of was disposed of the same way — by measuring the FLOOR or
the BAR and comparing the band to it, never by moving the band:

* `G4.3` — base model with no adapter scores `0.0001`–`0.0011` nats/token (`D-S4-9`), so the
  fine-tune bought the conditioning and the gap to `0.15` is the threshold's.
* `G4.6` — the alpha sweep showed a `10^-3` drift floor, an order of magnitude above the
  `1e-4` band, and `D-S4-13` then proved it is bf16 rounding, not a merge defect.
* `G4.4` — `D-S4-14` measured a seed spread of `0.142` and shipped the ratio as a band.

**`G4.1` has never had a noise floor.** Every "resolved / not resolved" call about it —
`FINDING 37` refusing a PASS at 0.61x "the spread", the `D-S4-5` entries refusing both the
FAIL and the PASS on `uk` against spreads of `0.131` / `0.391` — leans on a spread taken
from a pair of TRAINING runs, which confounds sampling variance with the fact that two GPU
training runs are not bit-identical.

And `D-S4-14` has just made this urgent: on `G4.4`, the seed alone moved the evening ratio
by `0.142`. `G4.1` is computed on the same ancestrally sampled text (`do_sample=True`,
`temperature=1.0`, `top_p=1.0`) from the same 600 diaries. If the seed alone can move
`G4.1`'s worst ratio by an appreciable fraction of the band's width (`0.80`–`1.25` is
`0.45` wide), then `1.456` and `2.293` mean different things and `it`'s single PASS may be
a seed.

## 3. The script already exists and has never been run

`tools/4thJ_step4_g41_seedfloor.py` (244 lines) + `.sh`, written 2026-08-20, `py_compile`
and `bash -n` clean, **never shipped, never executed**. It was held back because it wants
the same `nvidia_a100_2g.20gb` slice the training chain held. **The chain is finished and
the GPU is free.**

What it does:

* loads ONE frozen adapter ONCE and never trains, so weight divergence is exactly zero by
  construction and only `model.generate`'s sampling is left moving;
* re-generates under five seeds fixed IN THE SOURCE before any result existed
  (`13,101,1009,7919,104729`), so the set cannot be chosen to widen or narrow the spread;
* imports the TRAINER's own `gate_g4_1` and `generate_samples`, so the number is on the
  same basis as the readings it calibrates — and it therefore inherits the `D-S4-8`
  `eos_token_id` repair automatically;
* ASSERTS the prefix draw is identical across seeds and hard-FAILs if it moved;
* carries a vacuity guard: two seeds returning byte-identical text is a FAIL, never
  "`G4.1` has no sampling noise";
* writes `is_a_verdict_for_any_fold: false` into its own JSON.

Cost: generation only, ~600 diaries x 5 seeds, no optimiser, no checkpoints. Minutes to an
hour, one GPU job.

🔴 The result is a **LOWER BOUND** on the run-to-run spread of two trained replicates and
must always be quoted as one, never as "the" spread.

## 4. Options

**(a) Run the seed floor on all three folds. [RECOMMENDED]**
Three `sbatch` jobs, Leg-5 adapters, `--gen-n 600` as the folds were scored. Gives
`G4.1` the resolution every other Step 4 gate already has, and tells us directly whether
`it`'s lone PASS survives a change of seed. Same shape as `D-S4-9` / `D-S4-3` / `D-S4-14`,
all of which the author has already ruled. Nothing is re-scored, no band moves, no fold
verdict changes whatever the number is.

**(b) Run it on `it` only.**
Cheaper, and `it` is where the interesting reading is (the only PASS). But a floor measured
on one fold cannot be quoted beside the `es` and `uk` readings, and the folds differ in
sample composition, so it would buy one answer and leave two gates un-calibrated.

**(c) Skip the floor; declare `G4.1` FAIL as a model finding and close Step 4.**
Defensible — `G4.1` FAILs on two folds regardless of noise, and the band is frozen. But it
would be the ONLY Step 4 gate closed without knowing its resolution, and `it`'s PASS would
ship unexplained next to two FAILs. It also leaves `FINDING 37` and the `D-S4-5` refusals
resting on a confounded spread that we now know how to un-confound.

**(d) Raise N per fold instead of varying the seed.**
Would shrink the noise rather than measure it — but N was fixed at 600 when the folds were
scored, so this is a basis change after scoring, the same thing `D-S4-11` and `D-S4-14`
both ruled against. **Recommended against on precedent.**

🟢 **Option (a) — YES: Run the seed floor on all three folds (`es`, `uk`, `it`).**
