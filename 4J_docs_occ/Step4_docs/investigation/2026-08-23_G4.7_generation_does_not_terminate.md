# `G4.7` — why the Leg-5 model does not stop generating

**Investigation opened:** 2026-08-23
**Trigger:** Step 4 **Leg-5, fold `es`**, job `1286209`, `COMPLETED` 2026-08-23 07:31:50, elapsed `11:00:05`.
`G4.7` FAILed at every one of the three validation epochs — `107/600`, `138/600`, `127/600` terminated.
Leg-4 read `600/600` on all three folds.
**Status:** ROOT CAUSE **PROVED** on the cluster (job `1286484`, §9.2). `D-S4-8` **RULED (e) + (d) AND APPLIED** 2026-08-23 — see §7. 🔴 The repair is in the code but has **not yet been seen working**: the two-arm fix-check is job `1286491` (§10).
One decision is owed (`D-S4-8`, §7). The fix is **one argument**.

---

## 0. One paragraph

The model is **not** failing to emit `<eor>`, and the stop criterion is **not** failing to fire. **All
600 of 600** generated texts contain `<eor>`; the replay (§9.2) shows `StopStringCriteria` returning
`True` at the first `<eor>` in **16 of 16** sequences. The defect is one line further on: in
`transformers._sample`, the statement that overwrites the tokens of an already-finished sequence with
`pad_token_id` is guarded by `has_eos_stopping_criteria`, which is true only when an `EosTokenCriteria`
is present, and `generate()` adds one only when `generation_config.eos_token_id` is set.
🔴 **`Olmo-3-1025-7B` ships a `generation_config.json` with no `eos_token_id`; `OLMo-2-0425-1B`
ships one with `eos_token_id: 100257`.** With the guard false, a sequence that has already stopped keeps
sampling real tokens until *every other sequence in its batch of 8* has also stopped, so it accretes
`;<eor>;<eor>;...` filler or a whole second diary. That is why the replay's token counts are identical
within each batch (`323,323,323,323` then `440,440,440,440`), why one sequence carries **84** `<eor>`,
and why only the last-firing member of a batch ends cleanly. Same trainer code, same tokenizer, same
environment, same `--gen-batch 8` in both legs: the only variable is a **five-line JSON file inside the
model repo**. `G4.7`'s rule is *"the generated sample terminates with `<eor>`"*, so it reads FAIL,
correctly, for what it measures.

## 2. What the failure actually looks like

Every one of the 600 texts was classified by what follows its **first** `<eor>`:

| | count | meaning |
|---|---|---|
| **A** stopped exactly at the first `<eor>` | **76** | the criterion fired — this is the intended behaviour |
| **B** ran on emitting `;<eor>;<eor>;...` filler | **137** | diary finished, model idled, harness never stopped it |
| **C** ran on emitting a **new, complete diary** | **387** | harness never stopped it; the budget did |

126 texts *end* with `<eor>`; only 76 of those end at the **first** one. The other 50 end at a later
one by luck of where the 1280-token budget happened to fall.

Verbatim tail of a class-B generation — the diary is complete and correctly closed, and then:

```
...;10,031,,at_home,2;300,011,,at_home,0;<eor>;<eor>;<eor>;<eor>;<eor>;<eor>;<eor>;<eor>;<eor>;<eor>;
```

Verbatim tail of a class-C generation:

```
...,83,81,at_home,0;<eor>10,021,,at_home,0;<eor>10,031,,at_home,0;<eor,83,81,at_home,0;<eor,,at_home,0;
```

The three most common 9-character strings immediately after the first `<eor>`:
`;<eor>;<e` (126), `10,031,,a` (130), `20,031,,a` (48). Note what precedes the failure in every case:
`>` followed by `;`, `1`, `2`, `3` or `4` — never `>` standing alone.

## 3. The mechanism

`4thJ_step4_train.py:728-736`:

```python
eor_ids = tokenizer(TH.G4_7_EOR, add_special_tokens=False)["input_ids"]   # [27, 24274, 29]
eos_arg = eor_ids[-1] if len(eor_ids) == 1 else None                      # None: multi-token
stop_kw = ({"eos_token_id": eos_arg} if eos_arg is not None
           else {"stop_strings": [TH.G4_7_EOR], "tokenizer": tokenizer})
```

`<eor>` is an **ordinary string**, not an added special token, so it tokenises to three ids and cannot
be expressed as `eos_token_id`. `FINDING 12` already established this and moved to `stop_strings`.

🔴 **The first suspect was this wiring, and it is innocent.** The reasoning below was the
opening hypothesis and is kept because §3.1 and §3.2 were built to test it; §3.3 disproves it with a
direct measurement. Read §3.3 for the actual cause — which is *not* in the four lines above but in how
`transformers` masks a finished row inside a batch.

*Opening hypothesis (H1), since disproved.* `transformers`' `StopStringCriteria` answers one question
per step: *does the sequence, as decoded, **end with** the stop string right now?* It was supposed to be
intolerant of a token that **overhangs** the end of the stop string: if the model's chosen final token
decodes to `>;` rather than `>`, the text ends `...<eor>;`, the criterion returns `False`, and at the
next step there is more text still, so it could never return `True` for that occurrence again. Job
`1286484` tested exactly that case and the criterion returned **`True`** (§9.2, `overhang '>;' -> True`).
The premise is false.

### 3.1 The tokenizer is not the variable — it is byte-identical between the two legs

Read directly off the cache: both snapshots symlink to the **same blob** for every tokenizer file.

| file | Leg-4 `OLMo-2-0425-1B` | Leg-5 `Olmo-3-1025-7B` |
|---|---|---|
| `tokenizer.json` | `blobs/5fe17212...cd57` | `blobs/5fe17212...cd57` |
| `vocab.json` | `blobs/51135344...9709` | `blobs/51135344...9709` |
| `merges.txt` | `blobs/354558ed...d781` | `blobs/354558ed...d781` |

🔴 So the two legs share one vocabulary exactly. Nothing about `<eor>`'s tokenisation changed; only
**which** tokens the model chooses changed.

### 3.2 What the vocabulary does and does not contain

Grepped out of `vocab.json` itself:

* `">;"` **exists**, id `66895` (also `">;Ċ"` 10342, `">;ĊĊ"` 19985, `">;čĊ"` 85209).
* `502` vocabulary entries contain `>` with at least one character after it.
* 🔴 **`0` entries have `>` followed by a digit.**

That last line was the first crack in H1: the overhang story could at best cover class **B**
(`<eor>;<eor>;...`, 137 cases, token `">;"`), and **could not** cover class **C** (`<eor>10,031,...`,
387 cases), because there is no `">1"` token for the model to hide the `>` inside. 🔴 The replay
then closed H1 entirely — the criterion fires on the overhang too. What this section still contributes
is a fact worth keeping: the `<eor>` occurrences in the generated text are **real, well-formed, at
clean episode boundaries**, and the model's ability to close a diary was never in question.

### 3.3 The mechanism, proved

Job `1286484` replayed 16 generations from the Leg-5 `es` adapter under identical wiring, keeping the
token ids the original run threw away. It kills two of the three hypotheses outright.

| | hypothesis | verdict | the measurement that decides it |
|---|---|---|---|
| **H1** | tokenisation overhang: the model hides `>` inside a merged token, so the stop string never matches | 🔴 **DEAD** | the hand-built check `overhang '>;' -> True`: `StopStringCriteria` fires *even with* the overhang. And `fires=True` in **16/16** sequences at the first `<eor>` |
| **H2** | `stop_strings` never fired; the clean endings are the model's own EOS being stripped by `skip_special_tokens=True` | 🔴 **DEAD** | `n_eos_emitted = 0`. Not one sequence emitted token `100257`. The criterion fired in all 16 |
| **H3** | something else in the harness | 🟢 **CONFIRMED, and identified** | token counts identical within each batch of 4 (`323x4`, `440x4`, `281x4`, `309x4`) while `first_eor_step` scatters from `73` to `439` |

**What H3 is, exactly.** Read verbatim out of the installed library on the cluster,
`/speed-scratch/o_iseri/envs/step4/lib/python3.10/site-packages/transformers/generation/utils.py`
(`transformers 4.57.6`, the same file both legs imported):

```python
# :1335   the criterion our harness asks for
criteria.append(StopStringCriteria(stop_strings=generation_config.stop_strings, tokenizer=tokenizer))
# :1336   and the one that is only added when the model's generation config names an EOS
if generation_config._eos_token_tensor is not None:
    criteria.append(EosTokenCriteria(eos_token_id=generation_config._eos_token_tensor))

# :2737   the guard, inside _sample
has_eos_stopping_criteria = any(hasattr(criteria, "eos_token_id") for criteria in stopping_criteria)

# :2835   finished sentences should have their next token be a padding token
if has_eos_stopping_criteria:
    next_tokens = next_tokens * unfinished_sequences + pad_token_id * (1 - unfinished_sequences)
```

`StopStringCriteria` has no `eos_token_id` attribute, so it cannot set the guard. The only criterion
that carries one is `EosTokenCriteria`, and `:1336` appends it **only** when the generation config names
an EOS. The batch loop itself ends correctly, when `unfinished_sequences.max() == 0`; but with the guard
false, `:2836` never runs, **nothing masks the finished rows in the meantime**, and their sampled tokens
are kept as real text.

Read directly from the two model caches on the cluster:

```
== OLMo-2-0425-1B   (Leg-4)      generation_config.json
{ "_from_model_config": true, "eos_token_id": 100257, "pad_token_id": 100277, ... }
== Olmo-3-1025-7B   (Leg-5)      generation_config.json
{ "_from_model_config": true, "transformers_version": "4.57.0" }
```

Both models' `config.json` *do* carry `"eos_token_id": 100257`; only the **generation** config differs,
and only the generation config is what `generate()` reads.

**Why Leg-4 never showed it.** Identical code, identical environment
(`/speed-scratch/o_iseri/envs/step4`), identical tokenizer blobs, identical printed
`eor_ids [27, 24274, 29]`, identical `--gen-batch 8`, and both logs print the same
`MULTI-TOKEN, wired as stop_strings`. Leg-4's own generated file shows free per-sequence lengths inside
a batch of 8 (`420, 361, 324, 681, 567, 275, 479, 496` characters) and **exactly one** `<eor>` in every
one of its 600 texts; Leg-5's shows them locked together (`795, 776, 790, 743, 767, 739, 756, 731`).
The padding guard was true in Leg-4 and false in Leg-5, for no reason the pipeline controls.
🔴 **The harness has never had a working multi-sequence stop; Leg-4's `600/600` was
`EosTokenCriteria` covering for it. This is `gates must be seen failing` in reverse: a green reading
produced by a model-repo default rather than by a working check.**

## 4. What this does NOT explain

**`G4.1` is not downstream of `G4.7`.** `G4.1` scores `at_home_share` variance per stratum over the
generated texts. Since a class-C text is two diaries concatenated, the obvious worry is that `G4.1`'s
FAIL is an artefact of the overrun. It is not. `G4.1` was recomputed locally against its own real
reference (the 54,114 held-in non-`es` corpus records, matching the count the run itself printed),
twice — once on the text **as scored**, once with every text **truncated at its first `<eor>`**:

| basis | scorable strata | below band | above band | worst low | worst high | verdict |
|---|---|---|---|---|---|---|
| as scored (full text) | 6 | 0 | 2 | 0.935 | 1.456 | FAIL |
| truncated at first `<eor>` | 6 | 0 | **3** | 0.982 | **1.614** | FAIL |

Truncating makes `G4.1` **worse**, not better — the overrun was *damping* within-stratum variance by
averaging two days together. 🔴 **Fixing `G4.7` will not fix `G4.1`. Do not write that it might.**

All six scorable strata are `it|...`; no `uk` stratum reaches `N >= 100` on both sides. Noted, not
investigated here.

**`G4.3`, `G4.6`, `G4.12`** also FAILed on this run (`G4.3` CE rise 0.1062 against 0.15 required;
`G4.6` `max_logit_diff` 7.279e-04 against 1e-04; `G4.12` CE rise -0.0000). Nothing in this
investigation touches them and no claim is made about them here.

## 5. What it costs

* **Wall clock.** Every non-terminated generation ran the full 1280-token budget instead of stopping
  where the diary ended. 🔴 The run wrote **no per-phase timings** — `training_metrics.csv` and the
  run manifest carry none — so the exact cost cannot be quoted, only bounded: 474 of 600 generations
  per pass, three passes plus the diagnostics pass, inside a job of `11:00:05`. Stated as a bound,
  not as a measurement.
* **The perturbation battery.** Because `G4.7` was already FAIL at baseline, the generation-side
  battery could credit only `G4.4` as *seen falling*; `G4.1` and `G4.7` were logged
  `VOID -- already FAIL at baseline`. The coverage clause still returned PASS, but this run
  demonstrated one gate, not three.
* **Step 7 is NOT affected, and shows the fix already works elsewhere in the project.** Checked, not
  assumed: `4thJ_step7_generate.py` is a **different generator**. It runs under vLLM and stops on
  `stop=[grammar.EOR]` (`4thJ_step7_generate.py:182`), which is a **string-level** stop applied to the
  accumulated detokenised text and therefore has no token-boundary condition at all. Across the 26
  Step 7 generation jobs on disk it reads `terminated with <eor> : 600 / 600` **26 times**. All of
  them ran `--leg 4` (the 1 B backbone) under CONSTRAINED decoding, so this is not a like-for-like
  comparison with Leg-5 — but it does establish that a string-level stop rule does not exhibit the
  defect. 🔴 Two outliers in those logs, `599/600` and `0/16`, are noted here and **not**
  investigated.

2. Every future run must **print** whether `EosTokenCriteria` is in the resolved criteria list, so a

## 9. Probes

### 9.1 `1286480` — tokenizer and criterion, CPU only (COMPLETED, `00:09:46`)

`4thJ_step4_g47_probe.py`, no GPU, no model weights. Verbatim:

```
transformers 4.57.6 torch 2.5.1+cu121
leg5_olmo3_7b    vocab=100278  eor ids=[27, 24274, 29]  pad='<|pad|>'/100277  eos='<|endoftext|>'/100257
leg4_olmo2_1b    vocab=100278  eor ids=[27, 24274, 29]  pad='<|pad|>'/100277  eos='<|endoftext|>'/100257

VOCABULARIES IDENTICAL: True  |v5|=100278 |v4|=100278  shared=100278

OVERHANG TOKENS (decode starts with '>' and is longer than 1 char): 265
  of which '>' + digit: 0 -> []

StopStringCriteria verdicts:
  clean: ... <e|or|>                 -> fires=True   tail='|60,011,,at_home,0;<eor>'
  one step past a clean <eor>        -> fires=False   tail='0,011,,at_home,0;<eor>10'
```

What this settles:

* the two legs share **one** tokenizer, to the byte — the tokenizer is not the variable;
* `pad` is a **real, distinct special token** (`<|pad|>`, 100277), not aliased to `eos` (100257), so
  padding after an early stop is stripped cleanly by `skip_special_tokens=True` and cannot be mistaken
  for generated content;
* `StopStringCriteria` **does fire** on a clean `<eor>` ending — the criterion is not broken in
  general;
* **`0` overhang tokens carry `>` followed by a digit**, so 🔴 **H1 is ruled out for class C**, the
  387-case majority. H1 survives only for class B, where `">;"` (id 66895) exists.

The `">;"` overhang case was NOT tested by this probe — the test was gated on the `>`+digit list,
which came back empty, so it was skipped. `1286483` tests it.

Also measured locally, on all 600: the three characters immediately **before** the first `<eor>` are
`,0;` in 593 cases (`32;` 3, `,1;` 2, `,6;` 2). Every single first `<eor>` therefore sits at a clean
episode boundary — there is no malformed context to blame.

## 10. 🔴 The fix-check — job `1286491`, and why it can VOID itself

Reading a repair off a guard's condition is not the same as seeing it work, and this project does not
accept the first for the second. `tools/4thJ_step4_g47_fixcheck.py` runs **both arms back to back** on
the **same** prefixes and the **same** seed, at `gen_batch 8`:

```
arm CONTROL : stop_strings only               <- what Leg-5 `es` ran
arm FIXED   : stop_strings + eos_token_id     <- the repair
```

Five checks, **pre-declared in the script's own docstring before it was first run**:

| # | Check | Why it is there |
|---|---|---|
| **0** | 🔴 **CONTROL must reproduce the failure** | A control that comes back clean cannot show anything was repaired. If this fails the script prints **VOID** and the FIXED arm must not be quoted |
| 1 | FIXED `ends_with_eor == n` | `G4.7` would PASS on this sample |
| 2 | FIXED `n_more_than_one_eor == 0` | the batch-padding fingerprint is gone |
| 3 | FIXED per-batch token counts **decouple** (spread > 0) | a spread of zero means rows are still locked to the slowest member of the batch — the defect itself |
| 4 | FIXED `n_eos_emitted == 0` | the EOS is here for its side effect on the mask. If it starts firing on its own it is cutting diaries short, and the fix is wrong |
| 5 | `contains <eor> == n` in **both** arms | `G4.16` unmoved; the arms differ only in the mask |

The two arms share a seed but are **not the same texts** — temperature-1.0 sampling diverges the
moment the mask changes what a finished row emits. This compares **distributions of termination**, not
texts, and that is all it claims. It is 16 sequences on the `es` adapter: a generation-side
demonstration, **not** a gate score and **not** a fold result.
