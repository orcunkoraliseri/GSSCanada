### Finding 1 — `G3.9` and `G3.10` FAIL at baseline, one root cause: the `scheme` field

Not two problems. One.

`gate_g39` (`tools/4thJ_gates_step3.py:589`) requires **exactly one** distinct `mode` and **exactly
one** distinct `scheme` across the whole corpus. Measured, from `gate_report_baseline.txt`:

```
distinct_modes:   paper_papi_self_or_parent_proxy_age3to10, paper_self_completion      (2)
distinct_schemes: eet_2009_2010, uktus_2014_2015, usodeltempo_2013_2014                (3)
```

`gate_g310` (line 610) forbids the literal string `YEAR` **or any four-digit year** anywhere in the
prefix, via `YEAR_RE = (?<!\d)(19|20)\d{2}(?!\d)`. Measured: `n_hits = 73254` — **every single
record**, no exceptions. The `examples` list (`"00001"`, `"00002"`, …) is `r.get("hid")`, i.e. the
household ID of the hit, **not** the offending substring; nothing is wrong with those IDs. The
offending substring is the `scheme` value itself: `eet_2009_2010` contains `2009` and `2010`.

So the `scheme` prefix field breaks both gates simultaneously: it varies by country (fells `G3.9`)
and it embeds the survey years in its own name (fells `G3.10`).

**Where the contradiction was introduced.** `4thJ_03_serialisation.md:110` still asserts, in a 🔴
clause: *"`MODE` and `SCHEME` are constant across the entire training corpus (paper self-completion;
ACL 2008/2010)."* Line 96-97 of the same table say "constant across the corpus, `G3.9`". That was
true when the corpus was conceived as one harmonised HETUS instrument. It is **false** for the
corpus that Step 2 actually shipped, where `scheme` carries the **national** survey name and its
field years, and `mode` carries the national collection mode. Decision 16's three-country design
invalidated the premise; the gate and the doc were never revisited.

`G3.10`'s stated intent (`4thJ_03_serialisation_val.md:46`, *"a temporal axis creeping back in"*,
derived from author decision 3, and `4thJ_03_serialisation.md:114`, *"There is no `YEAR` field and
there never will be"*) is about a **conditioning** field the model could extrapolate along. Whether
a survey's proper name happens to contain digits is a different question from whether the model is
given a time axis. The gate as coded cannot tell those two apart.

**This is not fixable by the manager**: `G3.9` measures a real property of the shipped corpus, and
per the standing rule a gate is never relaxed to make our own artefact pass. Ruled on as DECISION
D-S3-11 / D-S3-12 (below).

### Finding 2 — coverage clause FAILs: `G3.3` was never felled, and cannot be

`17 / 18` gates that PASS at baseline were felled by at least one perturbation. The one that was
not: **`G3.3`**, and the failure is structural, not an oversight in the perturbation list.

`G3.3` is implemented in `tokenizer_pass` (line 419-440):

```python
ids   = tok.encode(text, add_special_tokens=False)
detok = tok.decode(ids)
ids2  = tok.encode(detok, add_special_tokens=False)
if ids2 == ids: n_rt_ok += 1
```

That is **tokenizer idempotency** — a property of essentially every well-formed BPE tokenizer, and
**not** a property of our vocabulary, our codes, or our record format. `G3.3`'s only perturbation is
`tokenizer_swap` (val doc line 63; implemented at line 955, swapping in `gpt2` per Decision 8), and
`gpt2` is idempotent too, so it measured **PASS — "DID NOT FIRE"**. That row is additionally marked
`coverage_only` in the expectation table, so nothing else can be attributed to it either.

The consequence is that `G3.3` currently cannot fail for any reachable defect, which is the "a gate
that cannot fail" class. Its stated hazard (`val:39`, *"a vocabulary mismatch that silently mangles
codes"*, `RL05` failure mode 4) is a real hazard — but round-trip idempotency is the wrong
instrument for it: a tokenizer that mangles `311` into three separate tokens still round-trips
perfectly. Ruled on as DECISION D-S3-13 (below).

### Finding 3 — four `UNEXPECTED FALL` findings, all on `G3.1`; the decoder is stricter than the doc

`G3.1` fell under ten perturbations. For six of those the val doc expected it. For **four** the val
doc's table says `G3.1` must "stay clean":

| perturbation | val doc says `G3.1` | measured |
|---|---|---|
| `zero_pad_act4` | CLEAN (val:64) | **FAIL** |
| `strip_eor_1pct` | CLEAN (val:66) | **FAIL** |
| `zero_pad_cop2` | CLEAN (val:73) | **FAIL** |
| `spell_unknown_two_ways` | CLEAN | **FAIL** |

Three of these four were **predicted on paper before the run** and are already written down as
Decision 6 above, from reading `decoder.py`'s validation logic: `decode_episode` hard-asserts
`len(act)==3`, hard-asserts `cop_s == str(int(cop_s))` (no leading zero), and does not case-fold, so
`UNKNOWN` returns the literal string instead of `None`. The prediction held on the real 73,254-record
corpus. `strip_eor_1pct` is the **fourth** case, not predicted: a record with its terminator removed
no longer decodes to the canonical structure either.

The underlying reason all four fall is one design fact about `gate_g31` (line 357-389): it decodes
the perturbed text and compares it **field-by-field against the frozen canonical structure built
from `harmonised.parquet`** (`structures_equal`, line 384), not against a re-encode of the perturbed
pipeline. Under that semantics **any** mutation of the text differs from the source and `G3.1` falls;
the val doc's "must stay clean" column was written assuming self-consistency semantics
(`decode(encode(x)) == x` on whatever pipeline is in force).

Both readings are defensible in isolation. The shipped one is the stricter and, for a round-trip
exactness gate whose whole purpose is to prove nothing was lost relative to the source, the more
useful one. Per the standing rule this is reported as a genuine **Acceptance-Test-3 finding — the
shipped decoder is stricter than the val doc's narrative** — and is **not** repaired by relaxing the
decoder, softening `G3.1`, or quietly editing the val doc's expectation table. What it does require
is that the val doc's table be corrected to match measured reality, with the correction dated and
attributed, so the table stops predicting something false.

## Decisions
(what the task doc did not decide, and what was assumed -- every item below is a real gap the task
doc and val doc left open; none was resolved by moving a threshold or a perturbation)

1. **`--perturbation all` added as a legal value beyond `baseline` and the 21 named rows.** The task
   doc requires `baseline` to be "a named value, not a default" -- it does not forbid an additional
   `all` value that runs baseline + all 21 perturbations in one job. This was necessary to satisfy
   NO-PARKING: 22 separate `sbatch` submissions would mean 22 separate turns waiting on 22 JobIDs,
   which is exactly the parking pattern the rules forbid. One job builds every perturbation's copy,
   runs the full 16-gate/9-guard battery against each, and prints the coverage cross-tab and
   acceptance-test summary at the end. `--perturbation baseline` and each of the 21 individual names
   remain fully supported as single-variant invocations for re-running any one row in isolation.

2. **`copresence_availability.md` staged to Speed from the repo-local copy**, since it did not already
   exist there (only the CSV crosswalks did). It is the untouched, real file -- all 18 country x flag
   cells are `recorded` (confirmed by reading it this session), which means the "assert a flag a
   country doesn't record" perturbation (row 8) needs a MUTATED copy (one cell flipped to
   `not recorded`) to have anything to fire against; the real file alone cannot exercise G3.8's FAIL
   path since no country genuinely lacks a flag. The script builds that mutated copy itself, in its
   own `--out` directory, never touching the real file.

3. **G3.13's "Level-1 time budget" is operationalised as the first digit of the 3-digit `ACT` code**,
   with the literal string `"000"` (D-S3-9's null-activity code) treated as its own separate `NULL`
   category rather than folded into real codes starting with `0` (several real codes do start with
   `0`, e.g. `011`, `012`, `021` -- confirmed from `crosswalk_activity.csv`). Neither the task doc nor
   the val doc defines "Level-1" precisely; this is the most defensible reading of a coarse activity
   grouping from a 3-digit code, and it keeps the genuinely-null episodes from contaminating a real
   category's total.

4. **G3.1's "expected" side for the four loader-level perturbations that DROP rows/diaries is built by
   removing those diaries from the corpus copy entirely**, not by mutating the canonical comparison.
   Removing a diary from the corpus leaves nothing to compare for it, so G3.1's 100% threshold is
   computed only over what the (defective) corpus actually contains -- which is what "the corpus and
   the loader's frame agree perfectly" means in the val doc's own reasoning. The one COLUMN-level
   loader defect (drop `act2` for Italy only) is different: those diaries stay in the corpus, only the
   field is blanked, so G3.1's canonical/expected structure for that run is built from a COPY of the
   harmonised index with Italy's `act2` forced to null -- simulating that the loader's own frame never
   had the column, which is the only way G3.1 can "agree perfectly" with a column it was never handed.
   `G3.15(b)`/`G3.16` always read the real, untouched `harmonised.parquet` fresh, per the spec.

5. **The bit-order-reversal and `ACT2`-`'98'`-fill perturbations are implemented as parameter
   overrides to the SHIPPED decoder, not as hand-forked copies of `encoder.py`/`decoder.py`.**
   `decode_cop` and `decode_record` already take `bitpos` as an explicit argument, so "encoder and
   decoder together reverse the bit order" is exactly: store `reverse_bits_6(COP)` in the corpus text,
   then call the real `decoder.decode_record` with `bitpos' = {flag: 5-pos}` for THIS perturbation's
   `G3.1` check only (this is mathematically identical to a decoder that was independently rewritten
   with the reversed order -- worked out on paper before coding: reversing the 6-bit integer is exactly
   equivalent to relabelling every flag's position to `5-p`). `G3.14(b)` is unaffected by this override
   because it never touches `decoder.py` at all -- it reads the TRUE bit order from the crosswalk
   independently, which is the entire point of that gate. The `ACT2='98'` row uses the real decoder's
   output and then, ONLY inside `G3.1`'s comparison for this one perturbation, remaps a decoded
   `act2=='98'` to `None` before comparing -- simulating "the decoder was also told 98 means absent."
   `G3.15(a)` is unaffected (independent parser, its own 43-code legal set, `'98'` is not in it).
   🔴 **This is a modelling choice about how to FAITHFULLY SIMULATE "encoder and decoder together,"
   not a change to `encoder.py`/`decoder.py`'s actual shipped code, and not a change to any gate's
   threshold.** The shipped files are untouched on disk.

6. **Several perturbations are expected, on paper, to make the SHIPPED decoder fail `G3.1` even though
   the val doc's perturbation table lists `G3.1` under "must stay clean."** Worked out before running,
   recorded here so the result isn't mistaken for a bug in the battery:
   - **Zero-pad ACT to 4 digits** — `decoder.decode_episode` hard-asserts `len(act)==3`; a 4-digit code
     raises `DecodeError` on every affected episode, which the battery counts as a `G3.1` failure.
   - **Zero-pad COP to 2 digits (`07`)** — `decode_episode` hard-asserts `cop_s == str(int(cop_s))`
     (no leading zero); `"07"` raises `DecodeError`, likewise counted as a `G3.1` failure.
   - **Spell `unknown` two ways** — `decode_episode` does NOT case-fold; `LOC=="UNKNOWN"` falls through
     to the generic `else: loc_val = loc` branch and is returned as the literal string `"UNKNOWN"`,
     not `None`, which mismatches the canonical `None` built from the real null `loc_class` row.
   If the actual run reproduces these, they are reported as genuine Acceptance-Test-3 findings (the
   decoder is stricter/less tolerant than the val doc's narrative assumed), not silently absorbed.
   **No gate, threshold or perturbation was edited to avoid these outcomes.**

7. **V3.i is implemented as a guard on THIS BATTERY's own read of `harmonised.parquet`**, not as a
   re-run of the Step 3 build's loader. It loads the parquet fresh, prints per-country rows/diaries
   read against the pre-registered totals, and FAILs if it does not match exactly -- i.e. it protects
   against the gate battery itself silently scanning a subset, which is the "one level up" framing the
   guard's own text uses. It is not a re-simulation of a defective corpus-building loader; that is what
   the five loader-level PERTURBATIONS exist to inject, and `G3.15(b)`/`G3.16` are what catch them.
   Since none of the 21 perturbations mutate `harmonised.parquet` itself, V3.i is expected to PASS on
   every variant in this run, including the loader-level ones -- reported as such, not treated as a
   contradiction.

8. **The tokenizer-swap perturbation uses `gpt2`** (public, ungated, guaranteed downloadable, and
   already known from `4thJ_03_serialisation.md`'s tokenizer comparison table to have a materially
   different vocabulary and worse per-code token cost than OLMo/dolma2). Neither doc names a specific
   substitute tokenizer for this row.

10. 🔴 **Real bug found by the local smoke test and fixed before submitting**: `tokenizer_pass()`
    originally called `tok.add_tokens(add_tokens)` directly on the SHARED, CACHED tokenizer object
    (`tok_cache[MODEL]`, reused across baseline + all 21 perturbations to avoid re-loading OLMo's
    vocab 21 times). Since `add_tokens_act311` is perturbation #12 of 21 and `add_tokens()` mutates
    a tokenizer's vocabulary in place, every perturbation running AFTER it in the loop
    (`zero_pad_cop2`, `reverse_bitorder`, `act2_98_fill`, the four `loader_drop_*` rows,
    `spell_unknown_two_ways`, `null_perturbation`) would have silently inherited the added
    `<act311>` token and shown a spuriously inflated `len(tokenizer)`, failing their `G3.12` for
    the wrong reason. Fixed: when `add_tokens` is set, the script now loads a PRIVATE, uncached
    tokenizer instance for that one variant only, never touching `tok_cache`. Caught locally, not
    on the cluster, because the smoke test happened to include enough perturbations to make the
    contamination visible in principle -- though the tiny fixture wouldn't actually have shown a
    numeric symptom (transformers isn't installed locally to run this exact code path); the bug
    was found by re-reading the code while writing the smoke test's expected-value assertions, not
    by an assertion failure. Recorded because it is exactly the kind of ordering-dependent bug a
    "run everything in one job, reuse the loaded tokenizer" design invites.

9. **Held-out-split perturbation ("split by diary instead of respondent") rewrites the `split` field
   for every record using a diary-keyed (not respondent-keyed) rule**, deterministic and independent of
   the original split, so that some respondents' multiple diary-days land on both sides -- this is the
   most direct way to manufacture a nonzero respondent intersection without needing the original split
   assignment logic (which lives in the build script, not the gate battery, and must not be imported
   for the same reason the encoder/decoder must not be).
