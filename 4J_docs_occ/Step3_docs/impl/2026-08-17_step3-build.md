### 🔴 FINDING, acted on: `strat_age_band` values contain characters outside V3.c's declared alphabet
`Step2_docs/outputs_step2/crosswalk_strata.csv`'s `target_band` column (confirmed by direct read) shows
the actual `strat_age_band` values that land in `harmonised.parquet` are `11-14, 15-24, 25-34, 35-44,
45-54, 55-64, 65-74, 75+` -- containing `-` and `+`, neither in V3.c's declared alphabet (digits, comma,
semicolon, lowercase a-z, underscore, the prefix delimiters, `<eor>`). Serialised literally this would
refuse the whole corpus on its first prefix. **Handled in `encoder.py`/`decoder.py` via an explicit,
closed, two-way lookup table** (`AGE_BAND_MAP` / `AGE_BAND_REVERSE`, all 8 values enumerated, anything
else is a hard `EncodeError`): `11-14 -> 11_14`, ..., `75+ -> 75plus`. **This is an encoding-choice
decision (how to spell an already-decided categorical value), not a threshold move, an imputation, or a
new vocabulary token -- but the task doc and the val doc do not decide it anywhere.** Flagged here for
author/manager confirmation; not blocked on it because it is squarely B1's job (how the encoder spells
a field) and blocking would violate no-parking.

### Decisions this task doc did not make, and what was assumed
- **Prefix internal delimiter = comma; prefix/body delimiter = `|`.** The task doc shows the record
  shape with human-readable spacing only (`V3.c` confirms no whitespace is in the real alphabet). Comma
  was chosen because it is already in the declared alphabet and unambiguous: the decoder always splits
  on the first `|` before ever touching the prefix, so reusing comma inside the prefix cannot collide
  with the episode tuples' own commas.
- **Episode join: no separator, each episode self-terminated by `;`, exactly matching the convention
  already used by the accepted `4thJ_cop_measure.py`/`4thJ_act2_measure.py` measurements** that `G3.5`'s
  band was costed against. Not stated explicitly for the 5-field record in the task doc, but changing it
  would invalidate the token-cost measurements the record format is built on.
- **`mode`/`scheme` validated defensively, not transformed.** I could not find their literal string
  values anywhere in the docs before running on real data (they are carried through unchanged from Step
  1). `enc_safe_categorical` lowercases and asserts `[a-z0-9_]+`; if a real value fails that, the build
  job FAILs loud with the offending value printed, rather than guessing a transform the way `strat_age_band`
  needed one. This will show up in the job output if wrong.
- **Held-out split: by respondent, 90/10, seed 42.** Not specified anywhere in the task doc or val doc.
  A person's diaries stay entirely on one side because the split key is `(country, hid, pid)`, matching
  the requirement; the 90/10 fraction and seed are this agent's choice, recorded as an assumption, not a
  measurement.
- **No crosswalk join keyed by `country` was needed in the encoder itself.** `loc_class`/`act2`/`act`
  are already the mapped target values inside `harmonised.parquet` (Step 2 did the crosswalk joins); the
  only crosswalk read live here is `crosswalk_copresence.csv`'s `bit_position` (keyed by `shared_flag`,
  not by country) and `crosswalk_activity_secondary.csv`'s `target_code_2d` (also not country-keyed).
  `V3.g`'s "assert non-zero matched keys per country" therefore has no literal join site in this
  encoder to apply to; `country` is still lowercased on read per D-S2-16, and the loader-accounting
  block asserts non-zero, exact row/diary counts per country against the pre-registered totals, which
  is the closest analogous check this script can make.
- **Full-record token stats (prefix + episodes + `<eor>`) are what gets reported against `G3.5`'s band,
  not the bare episode-tuple form job 1255237 measured.** The pre-registered 238.0/580.0/751 baseline
  (and the re-based 300/700/1024 band) were explicitly measured/declared on the bare form (no prefix, no
  `<eor>`) -- see `4thJ_03_serialisation.md`. The actual `corpus.jsonl` records carry the 8-field prefix
  and the `<eor>` marker, which cost additional tokens the bare-form baseline never counted. **Flagged,
  not resolved**: `4thJ_step3_build.py` prints both the full-record numbers (the real thing that
  determines RL05 truncation) and a note that they are not directly comparable to the bare-form
  baseline. If the full-record numbers land outside the band because of this gap rather than because of
  `ACT2`/`unknown`/`64`, that is a finding for the author, not something this script decides.
- **`4thJ_step3_build.py` FAILs (does not emit the corpus) on**: a loader total mismatch, any non-100%
  round-trip, an explicit-null reconciliation mismatch, a non-zero split intersection, or a changed
  `len(tokenizer)`. It does **NOT** fail on `G3.5` band exceedance -- that is measured and reported only,
  per "if the corpus exceeds the band, report it and stop, do not move it," which is the author's/
  manager's call to make on the reported number, not this script's to make by silently aborting or
  (worse) silently truncating.
