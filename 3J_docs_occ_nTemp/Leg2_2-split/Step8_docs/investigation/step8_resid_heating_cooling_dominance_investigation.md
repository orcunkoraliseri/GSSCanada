# Step 8 — Residential Heating/Cooling Dominance Investigation (§4 Physical Plausibility)

**Authored:** 2026-07-07 · **Status:** **TRUE ROOT CAUSE FOUND 2026-07-08 (§11): metering artifact, not a thermostat/model bug.** `Cooling:EnergyTransfer` is built from `Zone Air System Sensible Cooling Energy`, which counts cold ERV ventilation air delivered to the zone as "cooling" — no compressor involved. The winter "cooling" that triggered this investigation was never mechanical cooling. Mechanism A (frozen 24.0°C setpoint) is hereby RETIRED as the winter-cooling explanation — §8.1's "confirmation" was reading the same artifact meter. Fix direction = metric fix (report/gate on end-use Cooling **Electricity** vs Heating fuel) + revert the fix-v2 injector override. History: fix v1 (IDF-template patch) FAILED smoke — injector bypass (§9); fix v2 (injector-level, §9.1 option 2) executed 2026-07-08 — both 1a and 1b FAILED smoke, DJF cooling unchanged across setpoints 24.0/28.0/40.0 (§10), which is what exposed the artifact.
**Why this exists:** user flagged, while reviewing the regenerated `step8_validation_report.html`
(job 1069196, §4 · Physical Plausibility), that residential cooling energy exceeds heating energy —
physically wrong for Canadian climate zones, where heating should dominate, especially in the
coldest zones. Gates `4.6-heat-order` and `4.7-cool-floor` both showed PASS, so the report gave no
warning. This doc traces the mechanism, pinpoints which pipeline step it belongs to, and lays out
fix options — no code or IDF has been modified.

## 0. The observed anomaly

From `3rdJ_08_simulation_2split_val.py::_gate_enduse_split` (gates 4.6/4.7), 2022 scenario, residential
channel only:

```
[PASS] 4.6-heat-order: Heating share by CZ (5A=0.03, 5B=0.03, 5C=0.01, 6A=0.05, 6B=0.05, 7A=0.09)
       rises mild→severe as expected
[PASS] 4.7-cool-floor: Non-zero cooling share present in ≥1 CZ (max 0.45)
```

Both gates pass because neither one compares heating to cooling directly: 4.6 only checks that
heating share is monotonically non-decreasing as climate severity increases (true, it rises 0.03→0.09),
and 4.7 only checks that cooling is non-trivially present somewhere (also true). **Neither gate can
ever produce a FAIL, and neither one would catch "cooling is 5–10x heating even in the coldest zone."**
This is a validator gap, not proof the simulation is fine.

## 2. Root cause — two confirmed mechanisms, both in the static input templates

### Mechanism A — the apartment prototype's cooling setpoint never relaxes in winter

The residential archetypes are NOT generated by this pipeline — they are static prototype IDFs
under `2J_docs_occ_nTemp/BEM_setup/Buildings_MTL_v242/`:

```
ASHRAE901_ApartmentHighRise_STD2022_Buffalo_NECB17_Z6_v242.idf
ASHRAE901_ApartmentMidRise_STD2022_Buffalo_NECB17_Z6_v242.idf
AttachedHouse+CZ6A+IECC+2024_NBC936_Z6_v242.idf
DetachedHouse+CZ6A+IECC+2024_NBC936_Z6_v242.idf
```

The two apartment archetypes are **ASHRAE 90.1 STD2022 US DOE commercial-apartment reference
buildings** (localized to NECB17), a fundamentally different modeling paradigm from the two
house archetypes (OS-HPXML-style, itemized-appliance). Verified directly in
`ASHRAE901_ApartmentHighRise_..._v242.idf`, lines 21925–21953 (`Schedule:Compact,
NECB-G-Thermostat Setpoint-Cooling`):

```
Through: 12/31,
For: Weekdays,
Until: 01:00,24.0,  Until: 02:00,24.0, ... Until: 24:00,24.0,
For: Saturday, ... (all 24.0)
For: Sunday, ... (all 24.0)
```

The cooling setpoint is a **flat, unconditional 24.0°C for every hour of every day, all year** — no
seasonal widening, no economizer/free-cooling credit, no winter lockout. The heating setpoint
(lines 21796-21873) does have a night setback (22°C day / 18°C 02:00–07:00) but is likewise applied
year-round with no distinct summer/winter blocks (that part is normal HVAC-schedule practice).
Because the setpoint never relaxes, **any time internal gains (continuous lighting/plug loads —
apartment lighting ≈2.15 W/m², equipment ≈5.0 W/m², schedule floor ~0.2 fraction, i.e. never fully
off) plus solar gains push a zone above 24°C, the model calls for mechanical cooling — including in
a Winnipeg January**, since the trigger is internal/solar heat, not outdoor temperature. This is a
real, known failure mode for apartment/highrise energy models when the setpoint schedule doesn't
relax seasonally: interior/core zones can show near-continuous cooling need regardless of climate.
The house archetypes don't show this because their internal-gain and setpoint profile (itemized,
lower continuous baseline) doesn't overwhelm envelope losses the same way.

### Mechanism B — one envelope is reused for all 6 climate zones; only the weather file changes

`resolve_cell()` in `3rdJ_08B_run_paired_mc.py:55-72`:

```python
def resolve_cell(arch_name, city_name):
    ...
    idf = _find_one(STEP8_BUILDINGS_DIR, ".idf", arch["idf"])   # depends ONLY on arch_name
    epw = _find_one(WEATHER_DIR, ".epw", city["epw"])           # city_name only picks the weather file
```

`STEP8_BUILDINGS_DIR` (`eSim_bem_utils_3J/main.py:81-82`) is a single fixed path, with the comment
directly above it: *"Residential IDFs — same v24.2 stock as J2 (no residential IDF changes for J3)"*.
There is exactly **one IDF per archetype**, localized to one reference climate (Buffalo/NECB17/Z6 for
apartments, CZ6A for houses) — used for **all 6 Canadian climate zones (5A–7A)**. Only the EPW
weather file swaps per city; the envelope (insulation, glazing, internal-gain schedules, setpoints)
is identical whether the "cell" is Toronto_5A or Winnipeg_7A. So the "Winnipeg_7A" results are a
Zone-6-envelope building driven by Winnipeg weather, not a code-appropriate Zone-7A envelope. This
doesn't create the heating<cooling skew by itself, but it means the CZ-to-CZ "envelope gets more
robust in colder zones" assumption implicit in a gate like 4.6 is not actually true in the model —
the monotonic heating-share rise across CZ is driven entirely by weather severity, not by any
envelope difference.

## 3. Which pipeline step is responsible

- **Step 7** (`3rdJ_07_aug_to_bem_2split.py`, `3rdJ_07_bemIntegration_2split_val.py`) — confirmed via
  grep that neither script references `.idf` at all. Step 7 only writes occupancy/schedule CSVs
  (`BEM_Schedules_2split_*.csv`). **Not responsible.**
- **Step 8** (`eSim_bem_utils_3J/integration.py`, `idf_optimizer.py`) opens the static IDF templates
  and injects the pipeline's occupancy-derived schedules, but explicitly **preserves** the templates'
  original internal-gain power densities (`_update_power_densities_from_original`,
  `integration.py:974-1022`, comment "Restoring ... Density ... for Physics Consistency"). Step 8
  does not set thermostat setpoints and does not choose a per-CZ envelope. **Step 8 propagates the
  problem but did not introduce the wrong setpoint/envelope values.**
- **The wrong assumption is baked into the static input templates themselves**
  (`2J_docs_occ_nTemp/BEM_setup/Buildings_MTL_v242/*.idf`), which predate the numbered 3J pipeline
  (carried over unchanged from the 2J single-channel pipeline, per the main.py comment).
- **Where a fix must be applied**: Step 8, specifically the archetype→IDF resolution logic
  (`STEP8_BUILDINGS_DIR` / `STEP8_ARCHETYPES` in `eSim_bem_utils_3J/main.py`, and `resolve_cell()`
  in `3rdJ_08B_run_paired_mc.py`) is the only place in the pipeline that selects and consumes these
  templates per cell — either by patching the static IDFs directly, or by adding override logic at
  the point Step 8 builds each run.

## 4. Recommended fix options (ranked, not yet applied)

1. **(Targeted, lower risk) Patch the apartment cooling-setpoint schedule.** Add a winter
   relief/economizer allowance (e.g., widen the cooling setpoint deadband seasonally, or add an
   air-side economizer object) to `ASHRAE901_Apartment{MidRise,HighRise}_STD2022_Buffalo_NECB17_Z6_v242.idf`
   so mechanical cooling isn't triggered by internal gains alone through a Canadian winter. Cheapest,
   most surgical; re-simulate only the affected 2 archetypes × 6 CZ campaign subset to confirm the
   heat/cool balance normalizes toward something like the SingleD profile.
2. **(More correct, higher effort) Give each of the 6 CZs its own code-appropriate envelope.**
   Source or build CZ5A/5B/5C/6A/6B/7A-specific IDF variants (insulation, glazing per NECB
   requirements for that zone) instead of reusing one Z6-localized template everywhere; make
   `resolve_cell()` CZ-aware. This also resolves Mechanism B, not just A. Bigger lift — likely a
   full 8,400-run residential re-simulation.
3. **(Validator-side, complementary — does not fix the sim) Add a real heating-vs-cooling dominance
   gate.** e.g. flag WARN/FAIL if cooling share exceeds heating share by some threshold in a
   heating-dominated CZ (6A/6B/7A), so a regression like this is caught automatically instead of
   passing silently through 4.6/4.7 as currently written.

## 9. Fix v1 (IDF-template patch) FAILED smoke test — injector is the real bottleneck (2026-07-08)

**What was tried:** Option 1 (§4) variant 1a — patch `NECB-G-Thermostat Setpoint-Cooling` in both
apartment IDFs to a seasonal 28.0°C (Oct-Apr) / 24.0°C (May-Sep) / 28.0°C profile, holding
`WinterDesignDay`/`SummerDesignDay` at 24.0 in every block for HVAC autosizing. Full execution
detail in `step8_coolfix_implementation_plan.md` Progress Log.

**Smoke test result: FAIL.** 4-run smoke (2 MidRise + 2 HighRise, Winnipeg_7A, 2022) showed DJF
cooling essentially unchanged from pre-fix (MidRise 18,123 vs 16,474 kWh; HighRise 34,479 vs
34,126 kWh — the gate required <10% of pre-fix).

**Root cause of the failure:** the patched static schedule never reaches the simulation. The
actual cooling setpoint used by the sim (`CoolSP_HH_*` in the generated `in.idf`) is a **flat
24.0°C for the entire year**. This is because a *separate* pipeline step —
`inject_setpoint_schedules()` in `eSim_bem_utils_3J/integration.py` (~line 1112), called from
`inject_schedules()` (~line 1996) — reprocesses whatever static schedule we hand it:

- `_read_constant_from_schedule()` (~line 1163) extracts a **single** "active setpoint" constant
  by scanning the schedule object's fields **in reverse and returning the first one that parses
  as a float** — i.e. whatever the *last* field in the object happens to be.
- `_build_setpoint_schedule()` / `_compact_setpoint()` (~lines 1181-1201) then build **one flat
  Schedule:Compact block for the whole year** (`Through: 12/31`) using that single constant during
  occupied hours and a fixed setback (27.0°C) during absent hours — there is no seasonal branching
  anywhere in the output.
- In the original (and our patched) apartment IDFs, `For: SummerDesignDay` is the **last** day-type
  block within every `Through:` group (confirmed by grep: order is
  Weekdays→Saturday→Sunday→WinterDesignDay→SummerDesignDay, repeated per block). Our patch script
  necessarily forces design-day types to 24.0 in *every* block (required so HVAC autosizing is
  unaffected) — so the "last field" always resolves to 24.0, no matter what the surrounding
  seasonal blocks contain.

**This falsifies the fix mechanism, not Mechanism A.** Mechanism A (frozen 24.0°C cooling setpoint
driving winter internal-gain-driven cooling) remains correctly diagnosed and independently
confirmed (§7, §8.1). What's wrong is the *implementation*: editing the static IDF template is not
sufficient, because a downstream code step collapses any schedule — seasonal or not — down to one
constant applied uniformly across the year. **Variant 1b (40°C lockout) would fail identically**
for the same structural reason and was not re-tested (provable from the code, not just from
re-running it). Any real fix has to change `inject_setpoint_schedules()` / `integration.py` itself,
not (only) the templates it reads from.

**2J note:** 2J has its own separate copy, `eSim_bem_utils_2J/integration.py` (not shared code with
3J), so this bug doesn't automatically propagate there — but the same "collapse-to-one-constant"
pattern should be checked when 2J's version of this fix is sequenced.

### 9.1 Candidate injector-fix options (sketched 2026-07-08, none implemented)

## 11. TRUE root cause (2026-07-08, manager diagnosis): `Cooling:EnergyTransfer` is the wrong meter — cold ERV ventilation air is being counted as "cooling"

The §10 dead end (DJF cooling identical at 24.0/28.0/40.0°C winter cooling setpoints) is fully
explained without touching a single HVAC control: **the meter itself does not measure what the
pipeline assumes it measures.** Diagnosed locally from the preserved smoke evidence — no new
simulation was needed.

### 11.1 What the apartment archetypes' HVAC actually is

From the MidRise IDF (`Buildings_MTL_v242_3Jfix/ASHRAE901_ApartmentMidRise_...idf`), each apartment
zone is served by **two independent air-side systems**:

1. An `AirLoopHVAC:UnitarySystem` (Fan:OnOff + `Coil:Heating:Fuel` + `Coil:Cooling:DX:SingleSpeed`,
   ~line 14595 onward, one per unit) — load-controlled by the zone thermostat. This is the only
   equipment the thermostat (and therefore our injector fix) can influence.
2. A **`ZoneHVAC:EnergyRecoveryVentilator`** (one per unit: 24 in MidRise, 46 in HighRise, ~line
   11018 onward, each with a `HeatExchanger:AirToAir:SensibleAndLatent`) — supply/exhaust fans + HX
   only, **no tempering coil, no thermostat linkage**. It delivers heat-recovered outdoor air to the
   zone regardless of any setpoint.

There are zero `SetpointManager:` objects because the unitary systems are load-controlled — that
part of the employee's lead was right (a ventilation air path independent of the thermostat), only
it's the zone ERVs, not a central DOAS coil.

### 11.2 The metering fact (structural confirmation)

`eplusout.mtd` from the smoke runs shows the meter composition directly (e.g.
`campaign_smoke_v2/MidRise__Winnipeg_7A/sample_001_HH80741/2022/eplusout.mtd:1130`):

```
Meters for 4112,G SW APARTMENT:Zone Air System Sensible Cooling Energy [J]
  OnMeter=Cooling:EnergyTransfer [J]
```

`Cooling:EnergyTransfer` = Σ over zones of **Zone Air System Sensible Cooling Energy** — the net
sensible energy *removed from the zone air by any air system in a timestep*, whatever the source.
In a Winnipeg winter, whenever internal gains float a unit above its heating setpoint (furnace off),
the ERV keeps blowing in air that even after ~70%-effective heat recovery is well below room
temperature. That negative sensible delivery is metered as "cooling" — **kilowatt-hours of
"cooling" with the compressor off and zero electricity consumed.** The DX coil's compressor never
runs in winter (and never did, even at the original 24.0°C setpoint — otherwise the §10 table could
not be flat across 24.0/28.0/40.0).

Magnitude sanity check: 24 ERVs × ~0.04 m³/s × ΔT ≈ 11 K post-HX at −15°C outdoor ≈ 13 kW
building-wide, vs. the observed DJF "cooling" of 16,474 kWh / ~2,160 h ≈ 7.6 kW average (ERVs are
occupancy-scheduled, not 24/7) — right order, right shape.

### 11.4 Why the control archetype looked clean, and what is actually still true

- **SingleD/houses have no per-zone mechanical ventilation air system** (infiltration/exhaust only)
  → no artifact → DJF cooling ≈ 0. The §8.1 "control" contrast that "confirmed Mechanism A" was in
  fact confirming *which archetypes have ERVs*.
- **Mechanism A is retired** as the winter-cooling explanation: the flat 24.0°C setpoint is a real
  fact about the templates but drives nothing in winter (zones never reached 24.0 with the furnace
  holding ~21). It still governs genuine summer compressor operation, where 24.0 occupied is a
  reasonable setpoint — no model change warranted.
- The *residual* cooling-heaviness in true end-use terms (136 GJ cooling elec vs 78 GJ heating gas
  annually for this run) is a **prototype characteristic** — dense ASHRAE internal gains
  (5.0 W/m² equip + 2.15 W/m² lights) + tight STD2022 envelope + ERV heat recovery suppressing
  heating — not a 9.8× absurdity. That ratio (~1.7 site-energy) is a paper-framing question, not a
  bug. Mechanism B (one Z6 envelope for all CZs) remains a separate acknowledged limitation.
